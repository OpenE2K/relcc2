# Speculative execution

E2K lets a compiler execute operations before it knows they are needed:

- **Control speculation**: an operation moved above the branch (or out
  from under the predicate) that guards it. Marked `,sm` (speculative
  mode, ALS bit 31; [bundle.md](bundle.md)), it does not trap: a fault
  makes its result a **diagnostic value**, which traps only if a
  non-speculative operation uses it.
- **Data speculation**: a load moved above a store that might write the
  same memory. A *lock* load records itself in a hardware table (DAM, the
  disambiguation memory); stores to the same bytes remove the entry; a
  *check* load later either does nothing (the early value stands) or
  reloads and sets `%MLOCK`, which an `rbranch` turns into a jump to
  compensation code.

Predication (`? %predN`, [control-transfer.md](control-transfer.md)) is
the third way to remove branches; it is not speculation and is covered
there.

## Diagnostic values [hw, source]

A register holds a 2-bit tag per 32-bit half (kernel `tags.h`): 0 is a
number, 1 marks the half as empty or diagnostic (below; the guide
simplifies this to one bit per half; the other values are
protected-mode pointers). Memory has
the same tags, one per 32-bit word, written by `,sm` stores and read
back only by the fill MAS ("Spill and fill" below). A diagnostic double
has tag 5 (both halves). The 4C fills
a failed load's result with `4afafafa4afafafa`; a failed division or FP
operation returns the result it computed with bit 30 of each half set
(`1.0 / 0.0` → `7ff0000040000000`, `1.0 / 3.0` → `7fd5555555555555`,
`7 / 0` → `400000004000000d`; the Elbrus-8C2 (v5) gives the same
except for a `faddd,sm` whose result becomes diagnostic, from a
diagnostic operand or an inexact result: high half `7ff80000` (a quiet
NaN with bit 30) where the 4C has `40000000`), and a
speculative operation on a
diagnostic operand computes on its bits as usual and then sets bit 30
of each half (`addd,sm` of `4afafafa4afafafa` and 1 gives `…4afafafb`;
`andd,sm` of it and 0 gives `4000000040000000`). Predicates have one tag
bit: a **diagnostic predicate** comes from a speculative compare of a
diagnostic value.

**Empty and diagnostic.** A half tagged 1 is diagnostic only when **its
bit 30 is set**. With bit 30 clear it is an *empty* value, which
non-speculative operations read as a number. The kernel defines both the
empty and the diagnostic single as tag 1 (`ETAGEWS`, `ETAGDWS`) and the
double as tag 5, with the internal-tag mask `0x4000000040000000` (kernel
`include/asm/tags.h`) [hw, `tools/abi/probes/ctxsig.c` section 3; the
4C, 8C2 and 2C3 agree].

`puttagd` refuses to make a diagnostic half: SIGILL, `ILL_PRVOPC` (the
`priv_action` exception, kernel `traps.c:935-941`), at the `puttagd`
itself. With tag 5 it refused 0x40000000, 0x4000000000000000,
0x4000000040000000 and 0x4afafafa4afafafa, and accepted 0, 1,
0x0afafafa0afafafa and 0xbfffffffbfffffff. Tag 1 (the low half) refused
0x40000000 and accepted 0x4000000000000000; tag 4 (the high half) did
the reverse. A non-speculative `addd` of an accepted value does not trap
and gives the value with tag 0. The kernel's empty registers are of this
kind: 0 with tag 5, in `%g16`–`%g31` after a system call and in a signal
handler ([kernel-interface.md](../abi/kernel-interface.md), "System
calls", "Signals").

The hardware keeps bit 30 set in every diagnostic value it makes. A
failed load gives `4afafafa`, a failed operation its result with bit 30
set, and a speculative operation on a diagnostic operand sets bit 30 of
each half of its result. `andd,sm` of `4afafafa4afafafa` with 0 gives
`4000000040000000`, with `0xbfffffffbfffffff` gives `4afafafa4afafafa`,
and with `0x0000ffff0000ffff` gives `4000fafa4000fafa`; `ord,sm` with 0
gives `4afafafa4afafafa`; each result traps a non-speculative `addd`. So
user code can neither make a diagnostic value with `puttagd` nor turn a
diagnostic value into an empty one.

What happens to a diagnostic operand ([hw] unless marked):

| Use | Not speculative | Speculative (`,sm`) |
|---|---|---|
| ALU or FP operand (`addd`, `faddd`, ...) | SIGILL, `ILL_ILLOPN` | diagnostic result |
| Compare operand (`cmpedb`) | SIGILL, `ILL_ILLOPN` | diagnostic predicate |
| Diagnostic predicate as an operation's condition (`? %pred0`, and `? ~%pred0` alike) | SIGILL, `ILL_ILLOPN`, at the operation | the operation runs and its result is diagnostic: an `addd,sm`, an `ldd,sm` (its register), a `cmpesb,sm` (its predicate) (`preds.c` `dg_*`; [predicates.md](predicates.md)) |
| Diagnostic predicate in `merge` | SIGILL, `ILL_ILLOPN` | diagnostic result (`dg_mrg*`) |
| Diagnostic predicate in `ct ? %pred0` | SIGILL, `ILL_ILLOPN` | — |
| `merge` choosing the diagnostic operand / the other one | trap / no trap [source] | diagnostic / no effect |
| Store data | SIGILL (calling-convention.md) | the store is done with the register's bits (a wholly diagnostic register stores `4afafafa4afafafa`) and tags; read back by an ordinary load the value has tag 0, by the fill MAS its tag ("Spill and fill") |
| Store under a diagnostic predicate (`std ? %pred0`) | SIGILL | **the store is done whatever the condition's polarity** (`? %pred0` and `? ~%pred0` alike), with bit 30 of each 32-bit half of the data set (42 → `400000004000002a`, `123456789abcdef0` → `52345678dabcdef0`) |
| Store address | SIGILL `ILL_ILLOPN` | SIGILL `ILL_ILLOPN`: `,sm` does not help |
| Store to an invalid address (not diagnostic): NULL, an unmapped page, a read-only page | SIGSEGV | SIGSEGV as well (`std,sm`, `stw,sm`; `si_code` `SEGV_MAPERR` at NULL, `SEGV_ACCERR` at the unmapped and the read-only page): **a store has no speculative form for its address**, so no store can run ahead of the test that guards it; a predicated store is the way to drop the branch (`spec.c` `stb_*`; the proof-of-concept back end's I36) |
| Non-speculative operation **under a false predicate** with a diagnostic operand (`addd %dr3, 1, %dr8 ? %pred0`, `%pred0` false) | no trap, no effect (true predicate: SIGILL) | — |
| Load address (a diagnostic base, a diagnostic offset or a base with one diagnostic half) | SIGILL `ILL_ILLOPN`, `si_addr` the instruction | diagnostic result, no kernel entry (`4000000040000000` on the 4C and 8C2, `400defad400defad` on the 2C3), also for mod 3; `rbranch ? %dt_alN` is taken with the load in ALC N (`memx.c` `da_*`) |
| `movtd` into a CTPR | no trap; taking the `ct` traps (SIGILL; control-transfer.md) | |
| 32-bit operation reading only a clean half | no trap (calling-convention.md) | |

The store rows come from `spec.c`'s `st_*` cases (4C, 8C2 and 2C3
alike). In a register a half tagged 1 is diagnostic when its bit 30 is
set (above); after a `,sm` store, an ordinary load of the word
returns those bits with tag 0, so through an ordinary load a diagnostic
value becomes an ordinary number; memory keeps the tag, and only the
fill MAS reads it back (below). A store under a diagnostic predicate
changes memory whatever its data.

Kernel exception → signal (kernel `traps.c`): `exc_diag_operand`,
`exc_diag_cond`, `exc_diag_ct_cond` → SIGILL `ILL_ILLOPN`;
`exc_diag_instr_addr` → SIGILL `ILL_ILLADR`; `exc_div` → SIGFPE
`FPE_INTDIV`.

So the rule for a compiler: everything computed from a speculative
operation stays speculative (`,sm`) until the guard is known; only then
may a non-speculative operation, store or branch use it, and only on the
path where the guard holds. A consumer predicated on the guard may stay
non-speculative: under a false predicate a diagnostic operand doesn't
trap (above; `spec.c` `use_add_pfalse`, 4C, 8C2, 2C3; the
proof-of-concept back end's I33), and lcc relies on it (`if (c) r = *q +
7`: `ldw,2,sm` then `adds,0 … ? ~%pred0` without `,sm`). So `,sm` is
needed only on consumers that run unconditionally. A program that faults under speculation gets
SIGILL at the first non-speculative use instead of SIGSEGV, SIGBUS or
SIGFPE at the faulting operation (source-compat.md).

### Spill and fill [hw: `memx.c` `fill*`, `ovw*`, `tldw*`; 4C, 8C2, 2C3]

A register that may hold a diagnostic value can be spilled only with a
`,sm` store (a plain store of it traps, above) and reloaded only with the
**fill** MAS, `ld… mas=0x4` without `,sm`: the one load that returns the
memory tags with the bits. lcc's spill code is exactly this (`std,2,sm`
to the slot, `ldd,N … mas=0x4` back; 14,740 fills in lcc 1.29.16's v3
system libraries) [lcc].

| Reload of a slot written by `std,sm` of a diagnostic doubleword | Result |
|---|---|
| `ldd … mas=0x4` in ALC0, 2, 3 or 5 | `4afafafa4afafafa`, tag 5: the diagnostic value again; an `addd` of it is SIGILL, an `addd,sm` diagnostic, `rbranch ? %dt_al0` taken, a plain `std` of it SIGILL |
| `ldd`, `ldd,sm`, `ldd,sm … mas=0x3`, the lock `ldd,sm … mas=0x4` | the same bits with tag 0: **the deferred fault is lost silently** |
| `ldw … mas=0x4` after `stw,sm` | tag 1 (one word) |

- The tag is per 32-bit word. A clean store to any byte of a word clears
  that word's tag only: after `stw` at +0 the fill reads tag 4 (high
  word still diagnostic), after `stw` or `std` at +4 tag 1, after `stb`
  at +1 tag 4, after `std` at +2 tag 0, after a full `std` or `std,sm` of
  a clean value tag 0. So a slot reused at a narrower width keeps the
  other word's tag: reload at the width the slot was last written.
- A fill costs what a plain load costs, and gas and the hardware accept
  it in all four load channels (v3, v5, v6); `mas_mod.c` had run only
  ALC0 with clean data.
- So for a compiler: spill every register that may be speculative with
  `st,sm` and reload every spill slot with the fill MAS (free); never
  reload such a slot with an ordinary load.

## Speculative operations [hw]

| Operation | Exceptional case | Result |
|---|---|---|
| `sdivd,sm` | division by zero | diagnostic (non-speculative: SIGFPE `FPE_INTDIV`, semantics.md) |
| `fdivd,sm`, `fmuld,sm`, `faddd,sm` | any FP exception whose `%pfpfr` flag is **not already set**: inexact (`1.0 / 3.0`), divide by zero, invalid (`0 / 0`, `inf − inf`), overflow, underflow | diagnostic; the flag is **not** set |
| same | the flag is already set | the normal result (`1/3`, `inf`, NaN), no change to the flags |
| same | no exception (`1.0 / 2.0`) | the normal result |
| `fdivd` (not speculative) | divide by zero | `inf`, the flag set (FP exceptions are masked) |
| `fdivd,sm` | an **unmasked** exception (`%pfpfr` mask bit clear: divide by zero, inexact), flag set or not | diagnostic; the flag is not changed |
| `fdivd` (not speculative) | an unmasked exception, flag set or not | SIGFPE (`FPE_FLTDIV` 3, `FPE_FLTRES` 6) |
| `faddd` (not speculative) of that diagnostic result | | SIGILL `ILL_ILLOPN` |
| `fxaddxx,sm`, `fxmulxx,sm`, `fxdivxx,sm`, `fxdivtsx,sm` [hw: `tools/isa-probes/sregs.c` `fp` and `dc`, the three machines] | the same rules, with **`%fpsr`'s flags and `%fpcr`'s masks** (`%pfpfr` doesn't matter): a new 80-bit flag, or any exception unmasked in `%fpcr` (with underflow unmasked, an exact tiny result too) | diagnostic; `%fpsr` unchanged |
| same | the `%fpsr` flag already set, masked | the normal result; `%fpsr` unchanged, C1 included (a divide that rounds up leaves C1 alone, where its plain form sets it) |
| `pfadds,sm`, `fdtoid,sm` | as `faddd,sm` (`%pfpfr`) | |

So a speculative FP operation never has a side effect: if it would set
a sticky flag or trap, it yields a diagnostic value instead. A program
that unmasks an exception (`feenableexcept`) therefore gets SIGILL, not
SIGFPE, when a speculated operation raises it, unless the compiler
checks the result with `%dt_al` (below) and redoes the operation
non-speculatively. The kernel starts every
process with all six flags set (`%pfpfr` `0x1fbf`, `%fpsr` `0x3f`;
AGENTS.md), so in practice speculative FP operations give normal
results. But after `feclearexcept`, almost every speculative FP result
is diagnostic (inexact is common) and the program gets SIGILL at the
first non-speculative use. lcc's `-fspec-fp` (its default) "may hide
some exceptional situations" [lcc-doc]; in fact lcc speculates FP
operations, divisions included, in most loops, and its code then dies
this way ("What lcc speculates" below).

Nothing records a suppressed exception [hw: `sregs.c` `fp`; qemu
`target/e2k/cpu-sregs.h`]. `%pfpfr` bits 26–31 (`die` … `dpe`, which
MCST's qemu calls deferred flags but never uses) stay unchanged both
when a speculative operation yields a diagnostic and when a later
non-speculative use traps (SIGILL `ILL_ILLOPN` at the using
instruction, with `%pfpfr` and `%fpsr` unchanged). Setting them changes
no result, flag or trap: the 136 `fp` lines run with them set match the
lines without them.

## Speculative loads [hw, source]

A load's speculation kind is set by `,sm` and the MAS `mod` field
(kernel `trap_cellar.h`, `mas.h`; qemu `mas-format.h`):

| Form | Kind | Valid resident page | Valid page not yet touched | Invalid address (NULL, unmapped, `PROT_NONE`, kernel) |
|---|---|---|---|---|
| `ld` | normal | data | page fault, data | SIGSEGV (`SEGV_MAPERR` 1 / `SEGV_ACCERR` 2) |
| `ld,sm` (MAS mod 0) | **semi-speculative** | data | the kernel pages it in (about 5,000 cycles) and returns the data | diagnostic |
| `ld,sm ..., mas=0x3` (mod 3) | **speculative** | data | **diagnostic**, no kernel entry | diagnostic |

Measured costs on the 4C:

- A speculative or semi-speculative load from a valid address costs the
  same as a normal load.
- An invalid address under a semi-speculative load enters the kernel
  once per invalid region (about 5,000 cycles for an unmapped page next
  to a mapping): the kernel then clears the "valid" bit in the page table
  at the largest level that covers the hole (`clear_valid_on_spec_load`,
  `mm/fault.c`), and every later speculative load there fails in the
  hardware without a trap (no extra cost). NULL and kernel addresses
  were free in our runs; a fresh `PROT_NONE` page cost 64 extra cycles
  once.
- A fully speculative (mod 3) load never enters the kernel, but returns a
  diagnostic value for pages the process has not touched yet, so code
  using it needs a recovery path [lcc-doc `-fspec-ld`].

**Accesses that cross into another page** [hw: `memx.c` `pc_*`, `pcq_*`;
4C, 8C2, 2C3]: an 8- or 4-byte access starting 4 (or 2) bytes before the
end of a valid page:

| Next page | `ld,sm` (mod 0) | `ld,sm … mas=0x3` | `ld`, fill | `st`, `st,sm` |
|---|---|---|---|---|
| `PROT_NONE` | **whole value diagnostic**, the valid bytes too (about 100 cycles) | diagnostic | SIGSEGV `SEGV_ACCERR` | SIGSEGV `SEGV_ACCERR`, **nothing written** |
| unmapped | whole value diagnostic, one kernel entry (5,000–5,700 cycles) | diagnostic | SIGSEGV `SEGV_MAPERR` | SIGSEGV `SEGV_MAPERR`, nothing written |
| valid, not yet touched | paged in, the data | diagnostic | paged in, the data | both parts written |

`si_addr` is **the first byte of the bad page**, not the access's
address. 16-byte accesses: on v5 `ldqp`/`stqp` check alignment first, so
any crossing one is SIGBUS ([semantics.md](semantics.md), "Memory, tag
and descriptor operations"); on v6 they behave as above, except a
low-confidence anomaly of `ldqp,sm` whose high half lies wholly in the
bad page ([hwbugs.md](hwbugs.md), "What our probes saw"). So code that
reads past the end of a buffer with speculative loads (string functions)
must use naturally aligned accesses, which never cross a page; an
unaligned one turns valid bytes diagnostic. Once, inside a full run on
the 4C, a mod 3 load crossing into a valid, touched page came back
diagnostic; 30 isolated runs on each machine always gave the data.

lcc's `-fsemi-spec-ld` (default) makes loads moved from under a predicate
semi-speculative; `-fspec-ld` uses fully speculative loads with
compensation code where semi-speculative ones are not allowed; the
kernel itself is built `-fno-semi-spec-ld` [lcc-doc, source]. In lcc
1.29.16's output (CoreMark, Linpack, probes at `-O3`) [lcc]:

| Options | Speculative loads | Prefetch | Data speculation |
|---|---|---|---|
| default, or `-fspec-ld` alone | `ld,sm` (mod 0) | `ldb,sm …, mas=0x20` | lock `mas=0x4`, check `mas=0x3` |
| `-fno-semi-spec-ld` | `ld,sm …, mas=0x3` with `%dt_al` recovery | `ldb,sm …, mas=0x23` | none |
| `-fno-semi-spec-ld -fno-spec-ld` | none | none | none |

### Recovery: `%dt_al` [hw, lcc, source]

`rbranch label ? %dt_alN` (ctcond type 8, = `ibranch ? %MLOCK ||
%dt_alN`; gas: `tc-e2k.c`) jumps when the **speculative operation in
ALC N of the same wide instruction** has a diagnostic operand. N is 0,
1, 3 or 4 (several may be given, `%dt_al01`); gas requires a `,sm`
operation with an explicit channel there. This is how a fully
speculative load reaches its compensation code. lcc's `if (c) r = *p +
1;` [lcc]:

```
{ cmpesb,0 %r1, 0x0, %pred0 ; ldd,2,sm %r0, 0x0, %r4, mas=0x3 }
...
{ rbranch .L49 ? %dt_al1
  add_addd,1,sm %r4, %r4, %r4, %empty ? ~%pred0   ! the check
  addd,2,sm %r4, 0x1, %r3 ? ~%pred0 }             ! the real use
.L53: ...
.L49: { ldd,0 %r0, 0x0, %r4 }                     ! compensation:
      ... { ibranch .L53 ; addd,0,sm %r4, 0x1, %r3 ? ~%pred0 }
```

The check is any speculative operation that reads the loaded register,
under the guard's predicate, writing `%empty`; the compensation block
repeats the load without `,sm` (so a genuinely bad address faults
there, and an untouched page is paged in) and recomputes what used it,
then branches back. Measured [hw]:

| Check in ALC N, `rbranch ? %dt_alN` | Branch |
|---|---|
| operand diagnostic (`mas=0x3` from NULL or an untouched page, `ld,sm` from NULL) | taken |
| operand valid | not taken, no cost |
| the check predicated off (guard false), operand diagnostic | not taken |
| diagnostic operand in another ALC than N | not taken |
| no `rbranch`: the speculative operation alone | no trap, diagnostic result |
| the operation's own result diagnostic (`faddd,sm` inexact with flags clear), operands valid | **not** taken |
| a diagnostic FP operand (`faddd,sm` of the above) | taken |

So `%dt_al` tests operands, not results: an FP result that turned
diagnostic is caught only by a later speculative operation that reads
it. A taken branch costs about as much as any taken `ibranch`, plus the
compensation code.

Unaligned loads (`ldd` from a 4-aligned address) work and need no
speculation [hw]. A load to `%empty` with `,sm` is a prefetch: lcc emits
`ldb,0,sm ..., %empty, mas=0x20` (semi-speculative) in its own
prefetches, while `__builtin_prefetch` with locality 3 may have no MAS
(timing.md, "Software prefetch") [lcc]; the kernel's
own prefetch uses mod 3 [source].

## Data speculation (DAM) [hw]

The protocol, as lcc uses it and as measured:

1. **Lock load**: `ldd,0,sm %addr, %off, %rN, mas=0x4` (MAS mod 4,
   "lock-check"), in **ALC0 or ALC3**. It loads and records an entry for
   its destination register. **`,sm` is required**: without it the load
   records no entry, so its check always reloads and sets `%MLOCK`
   (`k_nosm*` in `spec.c`: ALC0 and ALC3, two registers, nothing in
   between; found by the proof-of-concept backend,
   `docs/spec-poc-findings.md` I10).
2. **Stores**: any store that overlaps the entry's bytes, even partly
   (a 4-byte store into an 8-byte entry), removes it. Stores elsewhere
   do not.
3. **Check load**: `ldd,5 %addr, %off, %rN, mas=0x3` (MAS mod 3, "check
   and unlock"), in **ALC2 or ALC5** (other channels: SIGILL
   `ILL_ILLOPC`), into the **same register**.
   - Entry intact: the check does not access memory; `%rN` keeps the
     early value. It does not compare addresses: a check naming another
     address still keeps the lock load's value.
   - Entry gone: the check loads (from its own address) into `%rN` and
     sets `%MLOCK`.
   - The check removes the entry: a second check of the same register
     reloads and sets `%MLOCK`.
   - **A check is predicable.** Under a true predicate it acts as
     above; under a **false** predicate it does nothing, entry intact or
     lost: no access (no fault even from an unmapped address), no reload,
     no `%MLOCK`, the register keeps the early value. So a load moved
     above both its guard and a store gets its check **under the
     guard's predicate**: where the guard is false its value isn't used
     and nothing happens.
   - **`,sm` makes it no check:** `ldd,5,sm … mas=0x3` is the fully
     speculative load (as `ld,sm mas=0x3` elsewhere): it reloads even
     when the entry is intact, never sets `%MLOCK`, and gives a
     diagnostic value from an unmapped address (`spec.c` `kc_*`, 4C,
     8C2, 2C3; the proof-of-concept back end's I29).
   - **Distances:** the check may follow its lock load in the very next
     instruction, also with an intersecting store between them (each a
     cycle apart); it doesn't wait for the lock load's value, and a use
     of the register right after the check gets the right value at the
     lock load's latency. Two lock loads may share one wide instruction
     (ALC0 and ALC3): both keep their entries (`spec.c` `kd_*`, 4C, 8C2
     and 2C3 alike; the proof-of-concept back end's I30 and I40).
4. **Recovery**: `rbranch label` (= `ibranch label ? %MLOCK`) in the
   **same wide instruction as the check** jumps when the check reloaded,
   to compensation code that recomputes whatever already used the early
   value, then branches back. In principle, if nothing used the early
   value before the check, the check's reload is the recovery and no
   `rbranch` is needed; but the proof-of-concept backend saw a consumer
   one instruction after such a check get the early value (once in 1,000
   calls, inside a larger function, I11), and neither it nor our probes
   could reproduce that in isolation. lcc puts `rbranch` in the check's
   instruction except where nothing read the register since the lock
   load (2 checks in NPB BT and 4 in SP at `-O3` for v5, e.g. `{ ldd,2
   %r20, 0x98, %r1, mas=0x3; ldd,3,sm %r20, 0x98, %r13, mas=0x4 }`), and
   it lets two checks, in ALC2 and ALC5, share one `rbranch` (63
   instructions in SP, PolyBench floyd-warshall's kernel) [lcc; the
   proof-of-concept back end's P47]. Given I11, a compiler should keep
   the `rbranch` unless no use of the register precedes the check.

**Quad lock and check loads (v5+)** [hw: Elbrus-8C2, `spec.c` built
with `-DSPEC_V5`, `./spec-v5 v5`]: `ldqp,0,sm … %qprN, mas=0x4` with
`ldqp,5 … %qprN, mas=0x3` (and `rbranch`) work as the doubleword pair,
for all 128 bits: an intact entry keeps the early value, a store into
**either half** removes it and the check reloads the whole 16 bytes, a
store to the next 16 bytes doesn't. The lock goes in ALC0 or ALC3
(gas also accepts ALC2, where it records no entry), the check in ALC2
or ALC5; without `,sm` no entry; mod 7 works; a second check reloads.
Entries are per register, not per size: a doubleword check (`ldd …
%drN, mas=0x3`) of a quad-locked register finds the entry, and a
`stqp` over a doubleword entry removes it. A quad entry counts as one
of the 32: 32 quad locks always fit, 40 never do, and a 33rd is
sometimes kept (2 runs in 3; `q_cap33`).

**v6** [hw: Elbrus-2C3, `spec.c` and `./spec v5`]: every case gives the
8C2's result (values, tags, `%MLOCK`, flags, signals; only cycles
differ), with the same 32 doubleword entries (`k_cap32` kept, `k_cap33`
lost, every run). Quad entries vary more: 33 to 44 quad locks sometimes
keep the first entry and 48 never do. A compiler should count on 32
entries; a lost entry only makes the check reload. The distances above
(a check right after its lock, a use right after the check) and the
predicated check behave the same on the 2C3, though its loads take 5
cycles (`kc_*`, `kd_*`).

Other MAS kinds [hw; qemu `mas-format.h`]. For data speculation lcc
1.29.16 emits only the lock `mas=0x4` (always with `,sm`) and the check
`mas=0x3` [lcc]; its spill reloads use the fill (mod 4 without `,sm`).

| Operation | MAS mod | Channels | Effect |
|---|---|---|---|
| `ld,sm` | 4, lock | ALC0, ALC3 | semi-speculative load and lock: pages in an untouched page (a trap, so the entry is lost at once; the check then reloads) |
| `ld,sm` | 7, speculative lock | ALC0, ALC3 | fully speculative load and lock: diagnostic for an untouched page, no entry; the check then reloads (non-speculatively, paging it in) and sets `%MLOCK` |
| `ld` | 3, check and unlock | ALC2, ALC5 | as above |
| `ld` | 2, check | ALC2, ALC5 | as mod 3 but keeps the entry: a later check still passes |
| `st` | 3, store and unlock | ALC2 (ALC5 for quad) | stores and removes the entry of its **data** register |
| `st` | 5, unlock | ALC2 (ALC5 for quad) | removes the entry of its data register; **does not write memory** |
| `st` | 4, no check | any store channel | stores without removing entries: a later check of the overwritten bytes passes with the stale value |
| `ld` (not speculative) | 4, fill | ALC0, 2, 3, 5 | a load that also reads the memory tags: lcc's spill reload ("Spill and fill" above) [hw: `memx.c`, `mas_mod.c`] |
| `ld` | 6, I/O (MMIO) | ALC2, ALC5 | an access to I/O space, as the kernel's `inb`/`inw`/`inl` do (`asm/io.h`, `MAS_IO_OPERATION`, at `IO_AREA_PHYS_BASE + port`); privileged: SIGILL `ILL_PRVOPC` in user mode [hw] |
| `st` | 6, I/O (MMIO) | ALC2, ALC5 | the store form, the kernel's `outb`/`outw`/`outl` [source; not run here, see below] |
| `ld` | 2, 3 or 6 in ALC0 (reserved) | ALC0 | SIGILL `ILL_ILLOPC` |
| `ld`, `st` | 0 with `m1` (bit 4, 0x10) set | any | an ordinary access: `m1` is ignored |

**v6 encodings** [hw: Elbrus-2C3, `mas6.c` (`gen_mas6.py`); source:
kernel `asm/mas.h`, `trap_cellar.h`]. v6 gives bit 4 (`m1`) a meaning:
with `mod` 3 it is the load-acquire / store-release form (bit 6 `mt`),
otherwise bits 0–1 (`m2`) choose the kind:

| MAS | Operation | Channels | Effect on the 2C3 |
|---|---|---|---|
| 0x13, 0x53 | `ld` (load-acquire, `MAS_LOAD_ACQUIRE_V6`) | ALC0, 2, 3, 5 | an ordinary load that faults normally; a dependent chain takes **10.4 cycles a load** (4.8 plain) |
| 0x13, 0x53 | `st` (store-release, `MAS_STORE_RELEASE_V6`) | ALC2, 5 | stores; back to back 3.5–4.8 cycles a store (plain 1.0; lcc's release, `wait ld_c, st_c` + `st`, 15.8). **Under an erratum on E2C3 up to rev 2, ours included**: MCST's kernel uses `wait` + store there instead (hwbugs.md, `STORE_RELEASE`) |
| 0x10 | `ld,sm` | ALC0 | semi-speculative, as `mas=0x0`: pages in an untouched page, diagnostic for a page it may not read |
| 0x12 | `ld,sm` | ALC0, 2 | **fully speculative**, as `mas=0x3`: diagnostic also for an untouched valid page; without `,sm` SIGILL `ILL_ILLOPC` |
| 0x11 | `ld` ("watch for modification", `MAS_WATCH_FOR_MODIFICATION_V6`) | ALC0 only (ALC2: SIGILL) | an ordinary load; a store by the same thread to the watched word doesn't trap |
| 0x11 | `ld,sm` | ALC0 | **the lock load**, exactly as `mas=0x4` (`spec.c` `lk11*`, `k11_*` against `lk4*`, `k4_*`: values, `%MLOCK`, faults and untouched pages alike) |
| 0x13 | `ld,sm` | ALC0 | **the speculative lock**, exactly as `mas=0x7` (`lk13*`, `k13_*`) |

| 0x14, 0x15, 0x16 | `ld`, `st`, `ld,sm` with bit 2 (`ch1`) | ALC0, 2 | as 0x10, 0x11, 0x12 without it (ordinary, lock-style semi-speculative, fully speculative), same timing; no visible effect from user mode on L1-resident data |

The old lock encodings (`mas=0x4`, `0x7`) keep working on v6. That the
acquire and release forms order memory can't be told on hardware that
already keeps every order but store → load (atomics.md); lcc 1.29.16
uses none of the v6 forms. Not tried, on purpose (a contact's machine):
0x17 (`m1` with `mod` 7) and `mt` beyond the acquire/release forms.

Not tried, on purpose, on the shared machines: mod 1 (no address
translation), mod 7 in ALC2/5 and stores with mod 7 (MMU, cache and TLB
operations, kernel `asm/mas.h`), stores with mod 1 or 6 (MMIO), and the
lock-wait load with mod 5. Shipped user-mode code does run two of the
mod 7 stores: libgcc's `__clear_cache` the cache line flush (MAS 0xf)
and `ld.so` the I-cache line flush (MAS 0x17) (x86-support.md).

With mod 7 a load can move above both a branch and a store: the check,
placed under the guard, turns into a normal load whenever the
speculative lock failed. Both lock kinds have the same costs and keep
or lose entries in the same way. A check of an address the program
cannot read faults like a normal load (SIGSEGV), so it must stay under
the guard.

When a check fails, the compensation code its `rbranch` reaches runs
after the whole wide instruction of the check, that instruction's own
writes included: a register the check's instruction writes holds the
new value there (`tools/isa-probes/pocchk.c` `dam_comp_same_wi`; 4C, 8C2,
2C3). So any value the compensation reads must survive the check's
instruction itself, not just reach it (the proof-of-concept back end's
P30: a redone add's operand overwritten in the check's instruction gave
wrong bytes).

What keeps or loses an entry:

| Between lock load and check | Entry | Measured |
|---|---|---|
| nothing | kept | check: early value, no `%MLOCK` |
| store to the same bytes, full or partial | lost | reload, `%MLOCK` |
| store to other bytes | kept | at distances 8 B to 16 MiB + 8: no false conflicts |
| a store before the lock load | — | no conflict |
| a `call` (to a function that just returns) | kept | |
| a call deep enough to spill the register file (64 levels) | lost | `DAM_BELL` 1 ([monitors.md](monitors.md)); 2 levels: kept |
| a trap (page fault) | lost: the kernel clears the DAM on every page fault and context switch [source] | reload, `%MLOCK` |
| **the destination register overwritten** | **kept** | the check returns the overwritten value, no `%MLOCK` |
| check of another register, or no lock load | — | reload, `%MLOCK` |
| the register locked again (other address) | the newer entry replaces it | a store to the first address keeps the check passing; a store to the second fails it |
| 32 lock loads to other registers | kept | |
| 33 or more lock loads | the oldest entries evicted | the table holds exactly **32** (`DAM_OVFL` = locks − 32 after a clear, monitors.md) |

`mmurw %rX, %dam_inv` clears the whole table; lcc writes it at the exits
of functions that use data speculation [lcc]. An entry is keyed by the
physical register (window base + index; MCST's qemu, `cpu-dam.h`), so a
stale entry from another function could make a check pass wrongly; the
rule is that every check is preceded on every path by its own lock load
of that register, with no write to the register in between.

lcc pipelines loops with this (`a[i] = b[i] * 3 + a[i - 1]` without
`restrict`): the lock load runs a few iterations ahead in ALC0, the check
in ALC5 shares a wide instruction with `rbranch` to a two-operation
compensation block [lcc]. Options: `-fno-dam`, `-fno-swp-dam`,
`-fswp-dam-cc` (compensation code in pipelined loops; default at `-O3`),
`-fno-dam-call`, `#pragma no_dam`; the guide (6.5.4.2) recommends
`-fno-dam` when a profile shows the compensation code running often
[lcc-doc, guide].

DAM works together with **rotating predicates** in such a loop
[hw: `tools/isa-probes/p28.c`, 4C and Elbrus-8C2]: a hand-written
pipelined loop locks `a[j]` and puts its parity in `%pred0` in one
stage, checks it with `rbranch` one or two stages later (as `%b[2]`,
`%pred1`; `setbp psz` 1 or 2 and `abp` with `abn` every iteration), and
selects `±a[j]` on the rotated predicate; a store breaks every lock but
the first, so the compensation code runs in nearly every iteration. It
recomputes the predicate under the name it has at the check, branches
back past the check, and the loop goes on: 0 wrong results up to 648
iterations, with the consumer reading the predicate in the check's stage
or one stage (one rotation) later; without the recomputation every
compensated element is wrong. So `rbranch` out of the kernel and back
keeps `%b[]` and predicate rotation, the loop counters and the DAM
entries of later iterations consistent, and the compensation code only
has to redo every instance that used the early value, under the names
it has at the check (the proof-of-concept back end's P28, where GMP's
`mpn_bdiv_dbm1c` went wrong, is therefore in its compensation code).

## Costs [hw, guide]

| Situation | Cost |
|---|---|
| A speculative operation that succeeds | none |
| A speculative load from an invalid region, first time | one kernel entry (about 5,000 cycles); none afterwards |
| A semi-speculative load from a valid page not yet touched | a page fault, even if the value is never used |
| A check load whose entry survived | none (no memory access); a use of its register in the next instruction issues as if the check were not there (`kt_check_use` against `kt_nocheck_use`, 22 cycles both) |
| A failed check | the reload, plus `rbranch` into and out of compensation code |
| `rbranch ? %dt_alN` not taken | none |

The guide's example (6.4.3, `if (a) *a++`): 10 cycles with a branch,
6 with the load and add hoisted as `,sm`, 5 with a predicated store as
well.

## What lcc speculates [lcc, hw]

lcc marks a large share of every kind of operation `,sm`, FP and
stores included (`count_lcc_ops.py`, `speculative:` in
[lcc-usage.yaml](lcc-usage.yaml); lcc 1.29.16):

| Operations | lcc's v3 sysroot libraries | NPB W, PolyBench, Lua, SQLite, LAME at `-O3` (v3.4c; v6.2c3 alike) |
|---|---|---|
| Loads | 64% | 69% |
| FP arithmetic and conversions (`fmuld`, `faddd`, `fmul_addd`, …) | 74% | 62% |
| FP compares | 79% | 74% |
| FP divisions and square roots | 68% (`fdivd` 327 of 458) | 69% |
| Integer divisions | 64% | 72% |
| Integer compares | 66% | 68% |
| Other integer operations | 20% | 21% |
| Stores | 6.5% (`std` 7,785 of 93,779) | 7% |

A `,sm` operation is either speculated itself or only reads a value that
may be diagnostic (anything computed from a speculative operation must
stay `,sm` until the guard is known, above), so the counts mix both.
Compiling small patterns at `-O3` (v3.4c, v6.2c3) separates them:

- **FP in loops is speculated itself.** In a software-pipelined loop
  every FP operation is `,sm`, also with operands only in registers and
  no loads: `s = s * x + 0.5` gives `fmuld,sm`, `faddd,sm`; `if (i % 3 == 0) s += x / y; else s
  += x * y` and `if (y != 0.0 && (i & 1)) s += x / y` execute `fdivd,sm`
  on every iteration, by zero too, and select the result by predicate.
  The loop's result (a `faddd,sm` accumulator) is then copied with a
  plain `addd`: there is no `%dt_al` recovery.
- **In straight-line code lcc sometimes speculates FP:** `if (c > 0) r =
  (x * y) / (x - y)` is if-converted with `fmuld,sm`, `fsubd,sm`,
  `fdivd,sm`; `c ? x * y : x + y` and `p ? *p * y + 1.0 : 0.0` keep
  their branches.
- **Stores are never moved above their guard**, but a store whose data or
  predicate comes from speculative operations is `,sm`: predicated
  `std,sm` in pipelined loops (data from `fmuld,sm`, predicate from
  `fcmpltdb,sm`) and in data-speculation regions before the check
  (Lua's `lua_tolstring`). If that predicate is diagnostic, the store is
  still done, with corrupted data (above): a fault the program would
  have taken becomes a silent bad store.

**Consequence for FP exceptions** (hw, 4C, 8C2 and 2C3 alike;
`tools/isa-probes/specfp.c` with `specfp-kern.c`): a
program that clears the sticky flags (`feclearexcept (FE_ALL_EXCEPT)`,
or only `FE_INEXACT`) and then runs lcc `-O3` loop code with an inexact
result dies with SIGILL `ILL_ILLOPN` at the first non-speculative use: a
dot product, and a loop storing `b[i] / 3.0` under a condition, both
did. The same code built with `-fno-spec-fp` has no `,sm` FP operation,
runs correctly and sets `FE_INEXACT`. While the flags stay set, as the
kernel starts processes, speculation is invisible, and speculative
operations never set a flag, so `fetestexcept` reports only what
non-speculative operations raised. lcc users know `-fno-spec-fp` as the
fix for FP code that expects exceptions (owner).

A compiler can speculate FP as lcc does (fast, but code that clears or
unmasks FP exceptions breaks) or keep FP operations non-speculative
unless an option allows it; either way it needs an `-fno-spec-fp`
equivalent. A `,sm` store must not rely on a diagnostic predicate to
suppress it.

## Recovery points (binary translation) [hw, source]

Hardware support for MCST's x86 binary translator (the kernel's "binco",
which runs x86 code in a "secondary space"), not for compiled code. A
**recovery point** marks where a translated region can be restarted;
between it and its end the processor is in **generations mode**, in
which it tracks the region's loads and stores. Sources: the kernel
(`cpu_regs_types.h` `e2k_rpr_t`, `traps.c` `do_recovery_point`,
`ttable.c`, `fault.c`, `trap_table.S.h`, `sec_space.c`), gas
(`parse_srp_args`); measured with `tools/isa-probes/rp.c` on the 4C,
8C2 and 2C3. The guide doesn't describe it, and lcc never emits it.

- **Operations** (SS, bundle.md): `srp` (bit 27, "store recovery
  point"), `crp` ("clear"), and `slrp` (v3+, both bits, a loop recovery
  point); each may take a condition (`srp ? %predN`: the RPC entry,
  predicates.md), and under a false one does nothing.
- **`%rpr`** (state registers 0xa0 `%rpr.lo`, 0xa2 `%rpr.hi`), readable
  and writable with `rrd`/`rwd` in user mode (bits 0–2 of the IP read
  0). The kernel's layout: `lo` = IP (bits 0–47) and `stp` (bit 58);
  `hi` = BR (bits 0–27), a second BR image `tbr` (bits 32–59) and
  `tsrp` (bit 63). `srp` and `slrp` write the address of **their own
  wide instruction** to `lo` and the current BR to `hi` (with `setbn rbs
  = 4, rsz = 3, rcur = 1; setbp psz = 2`: `hi` = `0x810c4`); after `srp;
  crp` `lo` reads 0. Our `slrp` left `stp` clear.
- **What generations mode forbids**, from `srp` until `crp` or the next
  kernel entry (whose code runs `crp`, "flush generations table", and
  keeps `%rpr`):
  - v3 and v5 (4C, 8C2): an atomic lock-wait load (`mas = 0x7`, glibc's
    stdio lock) is SIGILL `ILL_ILLOPC`. Plain loads and stores, calls,
    returns and faults behave as outside it (a NULL load is SIGSEGV).
  - v6 (2C3): the recovery-point exception (`exc_recovery_point`, #31;
    SIGBUS `BUS_OBJERR` for a task the kernel doesn't know as binco)
    comes for the lock-wait load, for a fault in the region (a NULL
    load gave SIGBUS, not SIGSEGV), and on entering code that isn't in
    the instruction cache (the first instruction of `printf`, of
    `ld.so`'s `_dl_fixup`); the kernel calls the last kind "false
    exc_recovery_point exceptions … when loading instructions into
    L1$".
  - Memory is not rolled back: a store done before the exception stays
    (all three).
  - `srp` and `crp` cost nothing: a 5-instruction loop with both takes
    6.00 cycles an iteration, as without (`tools/isa-probes/native.c`,
    all three). On the 2C3 a region opened every iteration and closed
    only after 100,000 of them ended in the recovery-point SIGBUS in one
    run of two; one closed every iteration never did.
- **The kernel's part**: the translator registers a range and a return
  IP (`SET_RP_BOUNDS_AND_IP`). A trap inside that range in generations
  mode makes the kernel **drop** the trap's pending loads and stores
  instead of replaying them from the trap cellar, and return to the
  registered IP (the translator's recovery code); a store fault in the
  range is SIGBUS. `exc_recovery_point` reaches user code as SIGBUS
  `BUS_OBJERR` (except for binco on v6). `%rpr` is saved and restored
  with the x86 segment registers (`%cs` … `%ss`) for binco tasks and
  passed in `sigcontext` (`rpr_lo`, `rpr_hi`). Erratum
  `CPU_HWBUG_GENERATIONS_L2_PREF` (E16C rev 2, E8V7 rev 0): generations
  conflict with the L2 prefetcher, which the kernel turns off while the
  translator runs.

## Emulators

| | 4C | MCST's qemu | Community qemu |
|---|---|---|---|
| Diagnostic load result | `4afafafa4afafafa`, tag 5 | `4000000040000000`, tag 5 | `4afafafa4afafafa`, tag 0 |
| Speculative FP exception | diagnostic, flags unchanged | normal result, **flag set** | normal result, flag set |
| `sdivd,sm` by zero | diagnostic | diagnostic | 0, no tag |
| Non-speculative use of a diagnostic value | SIGILL | aborts ("exception handling is unimplemented") | no trap |
| DAM | as above | as above, but a trap does not clear it | not modelled: every check reloads and sets `%MLOCK` |
| Check load in ALC0/ALC3 | SIGILL | accepted | accepted |
| `%dt_al` | taken on a diagnostic operand | never taken | aborts ("%MLOCK \|\| %dt_alM" not implemented) |
| Store `mas=0x3` (store and unlock) | removes the entry | keeps it | DAM not modelled |
| Speculative lock (mod 7) from an untouched page | diagnostic | data (untouched pages are not modelled) | data, tag 0 |

MCST's qemu matches the 4C on everything except FP, traps, `%dt_al` and
the store-unlock store; never use either emulator to judge FP
speculation or the signals a program gets. Code recovering through
`%dt_al` still runs correctly under it, because its loads fail only
where the guard is false.
