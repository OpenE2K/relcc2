# lcc's builtins and intrinsics

What lcc offers C programs beyond GNU C for using E2K operations
directly, and its emulation of x86 intrinsics: the interface a GCC port
needs for source compatibility with code written for lcc.

Sources, and what they allow:

- **lcc's manual** (`doc/lcc/builtin_mcst.html` in every lcc tree,
  **lcc-doc**): every MCST builtin with its signature. The names and
  signatures are in [lcc-builtins.yaml](lcc-builtins.yaml), generated by
  `tools/isa-extract/extract_lcc_builtins.py`; the manual's descriptions
  are not copied.
- **lcc as a black box** (**lcc**): `tools/abi/probes/gen_builtins.py`
  compiles a call of every operation builtin with the lcc build of its
  ISA version and records what lcc emits, in
  [lcc-builtins-check.yaml](lcc-builtins-check.yaml).
- **lcc's headers are not a source.** `e2kintrin.h`, `e2kbuiltin.h` and
  the x86 and ARM intrinsic headers lcc ships say "Copyright ZAO MCST.
  All rights reserved", so nothing is copied from them; a GCC port must
  provide its own headers under the same names. Their names were only
  compared with the manual: the manual lists every `__builtin_e2k_*`
  name `e2kintrin.h` declares.

## What lcc provides

| Kind | Where | Count | Notes |
|---|---|---|---|
| Operation builtins `__builtin_e2k_<op>` | `<e2kintrin.h>` | 430 (v1 128, v2 10, v3 34, v4 3, v5 162, v6 54, v7 39) | one machine operation each, named after it; below |
| Memory access with a MAS | built in | 11 | `__builtin_loadmas_{8u,16u,32u,64u,128v}`, `__builtin_storemas_*`, `__builtin_pstoremas_128v` (v5+), with `__LCC_MAS_*` flags and a channel (source-compat.md) |
| CPU detection | built in | 5 | `__builtin_cpu_init`, `_is`, `_name`, `_arch` (deprecated), `__builtin_e2k_cpu_iset` (source-compat.md, "CPU detection at run time") |
| System registers | built in | 9 | `__builtin_e2k_get_cpu_mode`, `_set_cpu_mode`, `_rrq` (a register pair by name), the `%rwap`/`%rwsap` fields |
| Protected mode | built in | 14 | descriptor fields, subarrays, tag loads (`e2k128` only) |
| Compiler barriers | built in | 4 | `__builtin_read_barrier`, `_write_barrier`, `_mem_barrier`, `_barrier` (marked experimental by the manual) |
| x86 intrinsics | `<immintrin.h>`, `<x86intrin.h>` and the per-extension headers (MMX to AVX2, AVX-VNNI, FMA, FMA4, XOP, SSE4A, AES, PCLMUL, SHA, BMI, BMI2, POPCNT, LZCNT, F16C, TBM, ADX, RDSEED, 3DNow!) | — | implemented on E2K operations (below) |
| ARM NEON | `<arm_neon.h>` | — | present; `__ARM_NEON` is not predefined |

(Plus 7 SPARC E90 builtins the manual lists, irrelevant here.)

## Operation builtins [lcc-doc, lcc]

`__builtin_e2k_<op> (…)` performs operation `<op>`
([operations-v3.md](../isa/operations-v3.md) and the later pages say
what it computes). Operands and results are integers whatever the
operation's data: `unsigned int` for 32-bit formats, `unsigned long
long` for 64-bit ones, `long long __attribute__ ((vector_size (16)))`
(`v2di`) for 128-bit ones; a builtin is available from the ISA version
the manual lists it under, so code uses them under `#if __iset__ >= N`.
On a call:

- **346 of the 391 builtins up to v6 emit their own operation** and
  nothing else beyond moving arguments (lcc at `-O2`, v1–v3 builtins
  with the generic v3 lcc, v4 with `v4.8c`, v5 with `v5.8c2`, v6 with
  `v6.2c3`; lcc 1.29.16 has no v7 target, so the 39 v7 builtins are
  unchecked).
- **Constant arguments**: lcc requires a constant for the table of
  `plog`/`qplog` (argument 1; the call becomes `plog_0xNN`), the third
  argument of `pextrh`, `pinsh`, `pshufw`, `psllqh`, `psllql`, `psrlqh`,
  `psrlql`, the second of `pshufh` and of `prefetch`.
- **Built from other operations**: `pshufh` and the 64-bit `punpck*`,
  which are real operations on every version, come out as `pshufb` with a
  constant mask; the 128-bit `qpunpck{h,l}{bh,hw,wd,dq}` are not
  operations at all (binutils has none) and lcc builds them with
  `qppermb`; `qppackdl` of two arguments into a returned pair needs no
  operation.
- **Memory builtins** named after what they do, not after an operation
  (`ld_{32u,64s,128}_{be,t1,t2,nta,sm,cleartag}`,
  `st_{32u,64s,128}_{be,nt}`, `pst_128{,_be,_sm}`, `prefetch`,
  `clflush`): plain loads and stores whose MAS gives the variant (`_be`
  0x8, byte-swapped; `_t1`/`_t2`/`_nta` 0x20/0x40/0x60, cache hints;
  `_nt` 0x40 on v5, a plain store on v3; `_sm` speculative; `pst_128`
  is `stmqp`); `ld_128_*` is two `ldd` and a `qppackdl` on v5 (as lcc
  loads 128-bit data, timing.md); `prefetch` is `ldb,sm …, %empty` with a
  hint MAS; `clflush` is `wait st_c`, a store with MAS 0xf (`mod` 7, a
  cache-line flush: not run here) and `wait fl_c`.
  [semantics.md](../isa/semantics.md) and [timing.md](../isa/timing.md),
  "Memory", say what those MAS values do.

**The manual's signatures are wrong in ten places** (lcc rejects calls
written as documented; lcc-builtins-check.yaml, `lcc_signature` and
`manual_iset`):

| Builtin | Manual | lcc |
|---|---|---|
| `qpacksshb`, `qpacksswh`, `qpackushb`, `qpackuswh` | `(v2di, uint64)` | `(v2di, v2di)` |
| `qpfstofd`, `qpfstoid`, `qpfstoidtr` | `(v2di)` | `(uint64)`: two floats in 64 bits |
| `qpidtofs` | returns `v2di` | returns `uint64` |
| `prefetch` | returns `uint64` | returns nothing |
| `qpsrad` | under v5 | only for v6 (the operation is v6, operations-v6.md) |

A GCC port should follow lcc, not the manual, for these.

## x86 intrinsics [lcc]

lcc predefines the x86 feature macros on **every** E2K target, without
options: `__MMX__`, `__SSE__` to `__SSE4_2__`, `__SSSE3__`, `__SSE4A__`,
`__AVX__`, `__AVX2__`, `__AVXVNNI__`, `__FMA__`, `__FMA4__`, `__XOP__`,
`__AES__`, `__PCLMUL__`, `__SHA__`, `__BMI__`, `__BMI2__`, `__ABM__`,
`__POPCNT__`, `__LZCNT__`, `__F16C__`, `__TBM__`, `__RDSEED__`,
`__3dNOW__`, `__3dNOW_A__` (lcc 1.29.16 for v3, v5.8c2 and v6.2c3 alike).
So portable programs that pick an SSE or AVX code path by these macros
take it on E2K under lcc, through lcc's headers. Their implementation
maps each intrinsic to E2K operations; a sample (`-O2`):

| Intrinsic | v3 | v5 and v6 |
|---|---|---|
| `_mm_add_epi8` | 2 × `paddb` | `qpaddb` |
| `_mm_shuffle_epi8` | 2 × (`andd`, `pshufb`) | `qpand`, `qpshufb` |
| `_mm_movemask_epi8` | `pmovmskb` | `qpsgn2mskb` |
| `_mm_madd_epi16` | 2 × `pmaddh` | `qpmaddh` |
| `_mm256_add_ps` | 4 × `pfadds` | 2 × `qpfadds` |
| `_mm_fmadd_ps`, `_mm_fmadd_pd` | `pfmuls` + `pfadds` per half: **two roundings** | v5: `qpfmuls` + `qpfadds`, **two roundings**; v6: `qpfmas`, `qpfmad`, fused as on x86 |

So 128-bit intrinsics cost one `qp` operation on v5 and later and two
64-bit operations on v3, 256-bit ones twice that, and the FMA
intrinsics give results that differ from x86 in the last bit before v6.
Programs probing CPU features at run time (`cpuid.h` is there too) get
whatever lcc's `__get_cpuid` returns; not checked.

Unipro's clang does the same: it predefines 16 of these macros
(`-march=elbrus-v5`) and ships `e2k_wrappers/` headers. Its x86 headers
are LLVM's (Apache-2.0 with the LLVM exception; two also carry a Unipro
"all rights reserved" line) and call `__builtin_ia32_*` builtins, which
its `e2kbuiltin.h` maps onto E2K operations; that file, its
`e2kintrin.h` (424 of lcc's 428 names, plus one of its own) and `cpuid.h`
are MCST's, "all rights reserved", like lcc's. So in both compilers the
E2K-specific part of the x86 layer is proprietary; only the generic
wrapper headers are open.

## For a GCC port

- **Operation builtins**: provide `<e2kintrin.h>` with the 430
  `__builtin_e2k_*` names and lcc's signatures (lcc-builtins.yaml,
  corrected by lcc-builtins-check.yaml), each gated by `__iset__`, the
  constant-argument ones checked at compile time. Since each name is an
  operation of [binutils-ops.yaml](../isa/binutils-ops.yaml), most can be
  generated: one GCC builtin per operation, expanded to the instruction
  pattern, with the memory builtins as moves with a MAS.
- **The MAS, CPU-detection and barrier builtins** are a small fixed set
  (source-compat.md has the `__LCC_MAS_*` values and the CPU model
  table).
- **x86 and NEON intrinsics** are a separate decision (the owner's): lcc
  makes x86 SIMD code build unchanged by predefining the x86 macros and
  emulating the intrinsics, which software built for Elbrus may rely on;
  a port that doesn't will take those programs' generic paths instead.
  The same structure as lcc's and Unipro's would be GCC's own x86
  intrinsic headers (GPL with the runtime exception) over a new E2K
  implementation of the `__builtin_ia32_*` builtins they use (written
  from the x86 semantics and the E2K operation pages, not from
  `e2kbuiltin.h`); many map to one operation each (the table above),
  and GCC's generic vector extensions cover much of the rest.
