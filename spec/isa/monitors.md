# Performance monitors

E2K cores count hardware events in debug registers that Linux exposes
through perf. Emulators have none of this, so it is the way to see on
hardware what a program's instructions did: how many wide instructions
ran, how many cycles they took, how often the pipeline stalled and why,
DAM and cache behaviour.

Status markers:

- **[source]**: MCST Linux 6.1: `arch/e2k/kernel/perf_event/perf_event.c`,
  `include/asm/perf_event_types.h`, `cpu_regs_types.h`,
  `kernel/hw_breakpoint.c`; event lists in
  `tools/perf/pmu-events/arch/e2k/v3..v7/Events.json` (names, codes and
  Russian descriptions)
- **[hw]**: measured on the Elbrus 4C (elbrus-v3, kernel
  6.1.158-mcst-e4c, perf 6.1.128) by `tools/isa-probes/pmu.c` (loop
  kernels generated by `gen_pmu.py`; the helper is `pmu.h`)

## Registers [source, hw]

| Register | What | User mode |
|---|---|---|
| `%dimcr` | instruction monitor control: per monitor (DIM0, DIM1) `user`, `system`, `trap` (interrupt on overflow) and an 8-bit event number | `rrd` works |
| `%dimar0`, `%dimar1` | instruction monitor counters | **`rrd` works**: a program can read a running counter without a system call |
| `%ddmcr`, `%ddmar0`, `%ddmar1` | data monitor control and counters (DDM0, DDM1); MMU registers | `mmurr` is SIGILL |
| `%dibcr`, `%dibsr`, `%dibar0–3` | instruction breakpoints (valid and trap bits per breakpoint) and their status | |
| `%dimcr1`, `%dimar2/3`, `%ddmcr1`, `%ddmar2/3` | the third and fourth monitors of each kind | v7 only |

So a v3 core counts at most four events at once: two instruction-side
(DIM0, DIM1) and two data-side (DDM0, DDM1). Which events a monitor can
count is fixed per event.

## Using them through perf [source, hw]

The core PMU is `cpu` (`PERF_TYPE_RAW`). A raw config is `0xMMEE`: `EE`
the event number, `MM` the monitor: 0 DDM0, 1 DDM1, 2 DIM0, 3 DIM1, 4
either DDM, 5 either DIM. Events.json writes each event's allowed
monitors before the colon (`2,3:13` is EXEC on DIM0 or DIM1, config
`0x513`; `0x313` pins it to DIM1). `perf list` on the machine shows the
names (`perf stat -e exec,ticks ./prog`).

On the 4C `perf_event_paranoid` is 2: a user counts its own threads in
user mode only (`exclude_kernel`). That is enough for probes and
benchmarks.

- Counting a region in-process: `perf_event_open` disabled, then ioctl
  RESET/ENABLE/DISABLE and `read` around the code (`pmu.h`,
  `pmu_count`). The ioctl wrappers add a constant (35 instructions, about
  200 cycles); subtract an empty run or difference two lengths.
- Pin an event to DIM0 or DIM1 and read `%dimar0/1` directly
  (`pmu_dimar0`): the deltas match perf's count. The value is the raw
  counter of the CPU the thread runs on, so pin the thread
  (`taskset`).
- Sampling (`perf record -e cpu/event=0x313/u -c PERIOD`) records the
  IP of the instruction that overflowed the counter (the kernel takes it
  from the monitor, `dim_ip`). The kernel throttles to
  `perf_event_max_sample_rate` (100,000 per second on the 4C): a period
  of 1 records 668 of 142,000 instructions, so exact per-instruction
  counts can't come from sampling.
- Where samples land: an EXEC sample is on the instruction itself; a
  `TICKS` or `IB_NO_COMMAND` sample taken during a taken transfer's
  bubble is on the target and, less often, on the next one or two
  instructions. So per-block cycles put a taken `ibranch`'s cost in
  its target block, and per-site taken counts come from EXEC −
  `NO_CT_TAKEN` samples at the transfer (`tools/isa-score/profile.py`).
- Hardware breakpoints (`perf stat -e mem:ADDR:x`) count only the first
  hit after each kernel entry (3 counted for 21 calls): the kernel
  disarms the breakpoint on a hit and re-arms it through a single-step
  that doesn't fire for user code here. Don't use them to count.

## Events checked on the 4C [hw]

Figures per execution of a kernel's loop body, after subtracting an
empty loop (`pmu.c`).

| Event (config) | Counts | Evidence |
|---|---|---|
| `TICKS` (0x272) | cycles | `add8`: 8; `nop 7`: 8 |
| `EXEC` (0x313) | wide instructions executed (a `nop N` instruction is 1) | `add8`: 8; `nop 7`: 1 |
| `BUB_B_NOP` (0x21a) | cycles of `nop N` waits | `nop 7`: 7 |
| `BUB_B` (0x219) | cycles phase B is held (nops, stalls) | |
| `BUB_E2` (0x211) | **interlock stall steps; each costs 4 cycles** | `ldd` used 2 cycles early: 1 step, +4 cycles; `muld` used 3 early: 2 steps, +8 |
| `BUB_E2_MEM`, `BUB_E2_ALUn_MEM` (0x230, 0x231…) | steps waiting for a load result | `ld_use`: 1 |
| `BUB_E2_OPND`, `BUB_E2_ALUn_OPND` (0x23c, 0x248…) | steps waiting for an arithmetic result, by consumer channel | `mul_use`: 2 in ALC1 |
| `CONF_ALUn_OUT` (0x240–0x242, 0x350–0x352) | write-back conflicts in ALC n (timing.md) | `muld,0` then `addd,0` 2 cycles later: 1; `addd,2` instead: 0 |
| `IB_NO_COMMAND` (0x218) | cycles without an instruction to issue: taken `ibranch`es (6 each) and taken `ct`s waiting for their CTPR, nothing else in cached code (control-transfer.md, "Instruction fetch") | two taken `ibranch`: 12; a taken `ct` 1 cycle after its `disp`: 3 |
| `NO_CT_TAKEN` (0x220/0x320) | executed instructions without a taken transfer, so EXEC − `NO_CT_TAKEN` = taken transfers | gcc-claude CoreMark: 1.136 G sampled at transfer sites, 1.137 G from `perf stat` |
| `RBRANCH` (0x217) | taken `rbranch`, both `%MLOCK` and `%dt_al` | failed DAM check: 1; `%dt_al` on a diagnostic: 1 |
| `TRAPS` (0x216) | interrupts | 0 for hardware register-file spills |
| `BUB_B_RF_SPILLFILL` (0x267), `BUB_B_CHAIN_SPILLFILL` (0x266) | register-file and chain-stack spill/fill stalls | 64-deep recursion: about 4 and 2 per level; 2-deep: 0 |
| `DAM_LINE` (0x020) | lock loads entering the DAM | one per lock load |
| `DAM_BELL` (0x120) | checks that failed (`%MLOCK` set) | |
| `DAM_OVFL` (0x121) | lock loads that evicted an entry | 33 locks after a clear: 1; 48: 16 |
| `L1_QUERY` (0x000), `L1_HIT` (0x100), `L1_ST_QUERY` (0x101), `L1_ST_HIT` (0x001), `DTLB_QUERY` (0x010) | L1 and DTLB accesses | one `ldd`: 1 query, 1 hit |
| `COND_ALU_FALSE` (0x225) | **not** what its description says (operations cancelled by their predicate) | 4 per ordinary instruction, 0 for one with four operations predicated off, 5 with one off, 2 with six: unexplained, don't use |

Facts these gave about the core (also in the other spec files):

- A stall is a whole number of 4-cycle E2 repeats: the hardware
  mechanism behind timing.md's stall rule.
- The DAM holds exactly 32 entries; a 33rd lock evicts the oldest
  (speculation.md).
- A call deep enough to spill the register file loses DAM entries; a
  shallow call keeps them (speculation.md).
- Register-file and chain-stack spills happen without traps.

## v5 (Elbrus-8C2) [hw]

The events checked on the 4C keep their numbers on v5 (`TICKS` 0x572,
`EXEC` 0x513, `BUB_E2` 0x511, `NO_CT_TAKEN` 0x520, `CONF_ALU0_OUT`
0x540, `DAM_*`, `RBRANCH` 0x517; only `L1_HIT` 0x100 is gone), and the
monitor probe gives the same counts there, so `profile.py` works on v5
unchanged. v5's list (643 events) splits the caches further: `L1_REQUEST`
(0x404, either data monitor; "synchronous requests except qpword"),
`L1_LD_HIT` 0x100, `L1_ST_QUERY` 0x101, `L1_ST_HIT` 0x001, `L2_QUERY`
0x040, `L2_HIT` 0x140, `L2_ST_QUERY` 0x141, and MAU (memory access
unit) and L3 events. They showed that `ldqp` bypasses L1 (timing.md,
"Elbrus-8C2"). With more events than counters `perf stat` multiplexes
and scales the counts; ask for at most four at a time for exact ones.

## v6 (Elbrus-2C3) [hw]

The same event numbers work on the 2C3 (kernel 6.1.0-1.17-e2c3,
`perf_event_paranoid` 2, user-mode counting allowed), so `profile.py`
and `validate.py` run there unchanged (`--cpu 0`: two cores). `pmu.c`
built by the 2C3-tuned lcc gives the 8C2's `TICKS` in 134 of its 166
kernels. Every other one is a load consumed 3 or 4 cycles after it
(`ld_use3_*`, `ld2_*`, `ldstall_*`, `stallnop_*`, `mm_*`, the speculative
`dt_al*`): 4 cycles more, with one more `BUB_E2_MEM` stall step, since a
load takes 5 cycles on v6 (timing.md, "Elbrus-2C3"); besides those, a
`disp` with a false `ct` in its own instruction takes 2 cycles (3), and
64-deep recursion 20 more (1,717), counted as 10 `BUB_B_CHAIN_RET_NRDY`
(returns waiting for the chain stack to be refilled from memory, 0 on
the 8C2) and 23 more `BUB_B_IP_NRDY`. Its spills count as many
`L1_ST_QUERY` as `L1_ST_HIT` there (360), where the 8C2 counts 520
queries for the same 360 hits.

MCST's kernel lists two errata that bear on measurements (hwbugs.md):
data-monitor events can be lost on the E2S (`KERNEL_DATA_MONITOR`), and
on the 8C2 and the 2C3 the kernel turns the pipeline-freeze feature off
while monitors run (`PIPELINE_FREEZE_MONITORS`).
