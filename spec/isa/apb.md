# Array prefetch (APB)

The array access unit (AAU) runs a small program of `fapb` entries
alongside the main instruction stream. Each entry streams one array
into a region ("area") of the array prefetch buffer (APB); the loop body
then reads the elements with `movaX` operations in four dedicated
channels instead of loads. A `mova` takes no ALU channel and has a fixed
latency, whatever the memory latency. The AAU also has stores with an
address register that increments itself (`staa` + `incr`).

This page is what a compiler needs to use APB correctly: the program
format, what a `mova` reads, what stops the unit, how traps interact
with it, and what it costs. Encodings of the syllables are in
[bundle.md](bundle.md) (AAS, SS `bap`/`eap`, CS0 `ldisp`); loop mode is
in [control-transfer.md](control-transfer.md).

## Model [guide, source]

1. Write the AAU registers the program uses: array descriptors `%aadN`,
   start indices `%aaindN`, increments `%aaincrN` (`aaurw`/`aaurwd`/
   `aaurwq`, channels 2 and 5).
2. `ldisp %ctpr2, label` loads the program at `label`. Only `%ctpr2`
   can hold it.
3. `bap` ("begin array prefetch") starts it. From now on the AAU fetches
   each area's elements ahead of use, independently of the main stream.
4. In the loop, `movaX` operations read elements from the areas; a `mova`
   with `am = 1` advances its area by one step after the instruction.
5. The program ends when `%ctpr2` is overwritten (lcc writes
   `disp %ctpr2, disp=0x0` after the loop) or at the next call or return.

`eap` ("end array prefetch") pauses the program: a `bap` after it
resumes where it stopped [hw].

## The program [source: gas; hw]

An APB instruction is 16 bytes with no header: a left half (APS0 +
APLS0) and a right half (APS1 + APLS1), 8 bytes each. In assembly one
`{ }` group holds up to two `fapb` entries: the one written with `ct=`
is the left half, the one with `dpl=` the right half. gas fills an
absent half with zeros. The program follows the function's code (lcc
places it after the loop's prologue, jumped over, after `.align 8`).

```
	.align	8
.Lprog:
	{
	  fapb	ct=0, dcd=0, fmt=4, mrng=16, d=4, incr=1, ind=0, asz=3, abs=0, disp=0
	  fapb	dpl=0, dcd=0, fmt=4, mrng=16, d=3, incr=1, ind=0, asz=4, abs=0, disp=0
	}
	{
	  fapb	ct=1, dcd=0, fmt=4, mrng=16, d=2, incr=1, ind=0, asz=4, abs=16, disp=0
	}
```

APS fields (APLS is the 32-bit `disp`):

| Bits | Field | Meaning |
|---|---|---|
| 31 | `ct` (left) / `dpl` (right) | `ct = 1`: last instruction of the program; it must be set in the last instruction's left half. `dpl = 1`: the right half's other fields are ignored and its area streams the same array as the left half's, with a position of its own (channels 2 and 3 read element 0, then 1, as channels 0 and 1 do) [hw]; lcc always writes 0 |
| 30 | `si` | Secondary index, v1 only; gas rejects it on v2+ |
| 28–29 | `dcd` | "Data cache disabled" (kernel `aau_context.h`; the guide's "cd", flag disabling the cache memories): 0 all caches; 1 reserved; 2 DCACHE2 off; 3 DCACHE2 and ECACHE off [guide]. Values 1–3 return the same data as 0; a stream with 2 (4C) or 3 (both) leaves other cached data alone, where 0 evicts it (Timing) [hw]. lcc always writes 0: also under `#pragma vector nontemporal`, `-fcache-opt`, `-fcache-opt-l2` and `-floop-st-dcache-mode=nocache_wc_force`, in 1.29.16 for v3, v5, v6 and in 1.31.05 [lcc]; it bypasses caches only per access, through the MAS (timing.md, "Memory") |
| 25–27 | `fmt` | Element format: 1 byte, 2 half, 3 word, 4 double, 5 quad, 7 quad packed (both qemus accept 7 as a 16-byte format; on the Elbrus-8C2 any `mova` from an area with `fmt` 7 is SIGILL, `movaqp` or `movad`, `mrng` 16 or 32, so it is not a v5 format there). Used to scale the increment and to check alignment |
| 20–24 | `mrng` | Bytes a `mova` may read per step, from 1 to 31; 0 means 32 |
| 15–19 | `d` | Descriptor `%aadN` (0–31) |
| 12–14 | `incr` | Increment register `%aaincrN` (0–7); `%aaincr0` is always 1 |
| 8–11 | `ind` | Start-index register `%aaindN` (0–15); `%aaind0` is always 0 |
| 5–7 | `asz` | Area size: 64 × 2^asz bytes; gas accepts 0–5 |
| 0–4 | `abs` | Area base in the buffer, in 64-byte units; must be a multiple of the area size (gas checks) |

Instruction *i*'s left half describes **area *i*** and its right half
**area 32 + *i***, so a program has at most 32 instructions [source:
kernel `traps.c`, qemu]. The unit for `asz` and `abs` is the guide's;
no other source gives one, and lcc's programs fill each half with
exactly 32 units (`asz` 3 + 3 + 4 above = 8 + 8 + 16).

## Registers [source; lcc]

| Register | Count | Width | Meaning |
|---|---|---|---|
| `%aadN` | 32 | 128 | Array descriptor: base address in bits 0–47 of the low half (plus tag, rw bits); size in the high half up to v6 |
| `%aaindN` | 16 | 32 (v3, v4), 64 (v5+) | Start index in bytes; `%aaind0` = 0. Checked (`ind64`: base = array − 2³², index 2³²): the 8C2 reads the array, the 4C uses the low 32 bits and gets diagnostic values [hw] |
| `%aaincrN` | 8 | 32, sign-extended (v3, v4), 64 (v5+) | Step in elements; `%aaincr0` = 1. Checked (`incr64`: bytes, increment 2³² + 1): the 8C2 reads from `a + 2³² + 1`, the 4C from `a + 1` [hw] |
| `%aastiN` | 16 | as `%aaind` | Store index for `staa` |
| `%aaldiN`, `%aaldaN`, `%aaldv`, `%aaldm`, `%aafstr`, `%aasr` | | | Current positions and state; the kernel saves them on traps |
| `%aabfN` | 16 | | Write-only; "value for modification of AAU load flags" (binutils). A write of any value to one with bit 1 of N clear (0, 1, 4, 5, 8, 9, 12, 13) **stops the program at the next trap**: the running program goes on, but after any later trap or interrupt every `mova` gives a diagnostic value, in both halves; the others (2, 3, 6, 7, …) do nothing [hw, 4C and 8C2] |

`aaurwd` to a `%aad` sets the base and the rw bits and clears the high
half (qemu). User code can execute `aaurrd` on the 4C, but every
register read that way returned 0 [hw]; `aaurrq` of a `%aad` does read
the descriptor back: after `aaurwq` of (0x0123456789abcdef, 0x10) its
low half is `0x1800456789abcdef`, the base's 48 bits with bits 59–60
set (semantics.md, "Memory, tag and descriptor operations"; 4C and
8C2). The positions the unit keeps (`%aaldi`, ...) stay unobservable.

How lcc sets them up:

| | v3, v4 | v5, v6 |
|---|---|---|
| Array address | in the descriptor: `aaurwq %rN, %aadK` with the base in `%rN` and 0 in `%rN+1` | in a start index: `aaurwd %rN, %aaindK` (64-bit); the descriptor gets base 0 (`aaurw`) |
| Step | `aaurw n, %aaincr1` (elements) | `aaurwd n, %aaincr1` |

## What a mova reads [hw]

```
movaX,CH area=A, ind=I, am=M, be=B, %dst      CH = 0..3
```

Channels 0 and 1 read areas 0–31 (left halves), channels 2 and 3 areas
32–63 (right halves): `area` names the instruction, the channel picks
the half. The area's first element is at

```
start = AAD[d].base + AAIND[ind] + (unsigned 32-bit) disp
```

and each step adds `size(fmt) × AAINCR[incr]` bytes. A `mova` reads
`size(X)` bytes at `current + I`.

- **`disp` is zero-extended**: with base `lo + 64` and `disp=-64` (gas
  encodes `0xffffffc0`) the first `mova` reads `lo + 2³²`, not `lo`, on
  the 4C, 8C2 and 2C3 alike. Put a negative offset into the base or
  `%aaind`, and `disp` at 0 or above (lcc always writes `disp=0`).
- **Negative increments** (backward areas) work, but **on v3 an area may
  not go below its base**: with the base at the first element read
  (the highest) and `%aaincr1` = −1, the 4C's `movad`s give a diagnostic
  value (SIGILL at the first use), whether the increment was written
  with `aaurw` or `aaurwd`; with the base at the lowest element and the
  start in `disp` (56 for 8 doublewords; lcc's v3 code puts the base
  below the stream and its start in `%aaind`) it reads all 8 right. The
  8C2 and the 2C3 read both arrangements right (`aaurwd` of −1). Whether
  a 32-bit `aaurw` of a negative increment is sign-extended on v5+ was
  not tried on purpose: if not, the area would step 2³² elements, 32 GiB
  for doublewords (the warning below). So on v5+ write a negative
  increment with `aaurwd`, as lcc does (`pocchk2.c` `apb_*`; the
  proof-of-concept back end's I41).

| Behaviour | Observed |
|---|---|
| `am = 1` | Advances the area by one step after the instruction; several `am = 1` movas on one area in one instruction advance it once. Without `am` the area stays put |
| `ind` | Byte offset inside the step, 0–31: `mrng = 32` with `movad` at `ind` 0, 8, 16, 24 reads four consecutive doubles |
| `movab`, `movah`, `movaw` | Zero-extended |
| `be = 1` | Byte-swapped; for `movaq` the whole 16 bytes |
| `movaq,0 ind=I` | Low half from `I`, high half from `I + 8` (gas writes it as two AAS entries, `ind` I and I + 8, in channels 0 and 1); `movaq,2` likewise in channels 2 and 3 |
| `movaq` / `movaqp` | Quad registers; `movaqp` is v5+ (lcc uses it on v5, v6 with `fmt = 5`, `mrng = 0`) |

### Diagnostic results [hw]

While the program runs, a `mova` never traps (for one that runs after
the program stopped, see the next section). When it cannot deliver data
it writes a diagnostic value (tag 1 in both halves, bits
`eaed0f70eaed0f70`), which then behaves like any other diagnostic
operand. Cases seen:

| Case | Result |
|---|---|
| `ind + size > mrng` | diagnostic |
| `mova` wider than `fmt` (`movad` on `fmt = 3`) | diagnostic |
| Base not aligned to `fmt` (v3) | diagnostic. lcc versions loops or needs `-faligned` [lcc]; v5 allows unaligned 2, 4, 8 bytes and v6 16 bytes [guide, lcc-doc] |
| Two areas whose `abs`/`asz` overlap | diagnostic |
| Element in an unmapped page | diagnostic; no signal. The prefetch running past the end of an array into an unmapped page is harmless (lcc's loops over arrays that end at a `PROT_NONE` page are correct) |

The kernel handles an AAU page fault speculatively: it maps the page if
it can and otherwise marks the access invalid, without a signal
[source: kernel `do_aau_fault`, `mm/fault.c`].

## Stores into a prefetched array [hw]

The buffer is **not kept coherent with stores**. A `mova` returns what
memory held when the unit fetched the element, and a later store to it,
ordinary (`std`) or AAU (`staad`), doesn't change what the `mova` reads
(`st_*` cases: the element is overwritten after the first `mova` of a
stream, then read a few movas later):

| Element overwritten (read by `mova` number) | 4C | Elbrus-8C2 |
|---|---|---|
| 0, right after `bap` and its 21-cycle wait | old value | old value |
| 1, 2 (also after a further 64 cycles) | old value | old value |
| 7 | old value | **new value** |
| 40 (step 5 doubles, read by the 9th `mova`) | new value | new value |

Which stores a `mova` sees depends on how far the prefetch has run, so a
compiler must treat it as unpredictable: **use APB for an array only if
nothing writes, during the loop, an element of it that a later `mova`
reads**. Stores to elements already read are harmless. lcc keeps to this
[lcc, `-O3 -faligned`]: it uses APB for `a[i] = a[i] * 2` and for
`a[i] = b[i] * 2` with `restrict`; without `restrict` it versions the
loop on a run-time comparison of the pointers (`a ≤ b` among others)
before the APB version; it never uses APB for `a[i + 2] = a[i] * 2`.
Both qemus read memory when the `mova` executes, so they return the
stored value.

## Starting, pausing and stopping [hw]

| Between movas of one stream | Next `mova` |
|---|---|
| `call` (to a function that just returns) | **SIGILL** |
| `disp %ctpr2, ...` (any write to `%ctpr2`) | **SIGILL** |
| `eap` | **SIGILL** |
| `eap` ... `bap` | continues where it stopped |
| `disp %ctpr1, ...` | continues |
| `aaurw 0, %aabf0` | continues, until the next trap; after it, diagnostic |
| a page fault or a signal handler | continues, but see "Traps" below |

A call or return resets the AAU [source: qemu `translate-ct.c`; kernel
comments in `ttable.c`], so APB can be used only in loops without calls
[guide 6.6], and a `mova` after a call (even in a later, separate loop)
must follow its own `ldisp` and `bap`. System calls also reset it (they
are reached through calls anyway). The kernel itself is built with
lcc's `-fno-loop-apb` and keeps `%ctpr2` free in trap code.

After the loop lcc writes `{ disp %ctpr2, disp=0x0; aaurw,2 0, %aabf0 }`
and never uses `eap`. The `%aabf0` write marks the program finished for
the kernel's restart: any value, written to `%aabf0` (or 1, 4, 5, 8, 9,
12, 13), leaves the running stream alone, but after the next trap the
unit doesn't resume and every `mova` is diagnostic, in both halves of
the buffer (`aabf*_pf_*`, `aabfr*`, `aabf_signal`, with a page fault or
a signal handler between movas; written before `bap` it changes nothing
visible). A compiler should end every APB loop as lcc does.

## Traps, signals and the loop counter [hw, source]

The kernel stops the AAU on every trap and interrupt, saves its state
and restarts it on return [source: kernel `ttable.c`]. On return it does
not restore each area's position: it **recomputes** it as

```
start + step × iterations,  iterations = %ilcr.lcnt − %lsr.lcnt
                            (+ the epilogue count when lcnt reached 0)
```

(`kernel/cpu/iset_v3.c`; v6 saves the positions instead, and on the
2C3 a trap between movas outside a loop leaves them in place: "v6",
below). So the number
of `am` advances of every area must equal the number of loop-mode
iterations done, **at every instruction where an interrupt can arrive**.
Interrupts arrive at any instruction (timer, other CPUs), so this is a
correctness rule, not a corner case. `apb-loop.c` shows it on the 4C:

| Loop (sum of 1M elements, 200 runs) | Result |
|---|---|
| `loop_mode` loop counted by `%lsr`, one `am = 1` per area per iteration, `%lsr` written before `bap` | correct in every run, also with a SIGALRM every 100 µs (about 21,000 signals) |
| Ordinary branch loop with the same movas | wrong in every run, even without extra signals |
| `loop_mode` loop, but `%lsr` written after `bap` and a page fault between them, after a 777-iteration loop | the stream is shifted by exactly 777 elements; correct without the fault |

lcc's loops (`apb-lcc.c`: one array, two arrays with a stride and an
offset, a dot product) gave 0 wrong results in 900 with about 34,000
signals, and with three processes sharing one CPU.

Epilogue iterations count too: with `ldmc` = 1 the movas keep going in
them ([loops.md](loops.md)), and a loop of `lcnt` 8 + `ecnt` 31 that
sums its 39 elements through one area (`loopF`) gave the right sum in
all of a million runs with a SIGALRM every 100 µs (about 4,900 signals
on the 4C, 2,100 on the 8C2), so the kernel's recomputation also covers
interrupts in the epilogue. With `ldmc` = 0 the movas stop and the sum
counts the eighth element 32 times, as expected.

**v6 keeps the positions** [hw: Elbrus-2C3, `apb-loop.c`]: the ordinary
branch loop is correct there in every run (0 of 200 wrong under 12,294
signals; the 8C2: 200 of 200 wrong), and the stale-counter loop with a
page fault is not shifted. So on v6 an area may advance any number of
times per iteration, in any loop (lcc 1.31's `-floop-apb-packets`,
"available from Elbrus V6"). The rules below are for v3–v5.

Rules that follow (v3–v5):

- Use APB only in a loop counted by `%lsr` ([loops.md](loops.md);
  `ct %ctpr1 ? %NOT_LOOP_END`, `alc alcf=1, alct=1`), with every area
  advanced (`am = 1`) exactly once per iteration. The `loop_mode` bit
  itself is not needed: `apb-loop.c`'s `loopD`, `loopA` without it, is
  right in every run under about 20,700 signals on the 4C and 8,700 on
  the 8C2 (the PoC's pipelined kernels, which use no `loop_mode`, also
  pass).
- Write `%lsr` (which also sets `%ilcr`) before `bap`, and issue no
  `mova` outside the loop.
- In the prologue between `bap` and the loop, no area may advance.

## Timing [hw]

On the 4C (elbrus-v3), data in L1 or L2:

| | Cycles |
|---|---|
| `bap` → first `mova` without a stall | 22 (a `mova` issued earlier stalls in steps of 4 cycles; lcc leaves 17–24) |
| `bap` → first data from memory | about 160–250 more |
| `mova` → consumer | 5, in any channel or cluster; a consumer issued earlier stalls a fixed 4 cycles |
| `mova` issue | up to four per instruction, every cycle |

lcc's loops with and without APB (`apb-lcc.c`, ns per element at about
0.8 GHz; `-fno-loop-apb` turns APB off):

| Array | `sumd` APB | `sumd` no APB | `dot` APB | `dot` no APB |
|---|---|---|---|---|
| 16 KiB | 0.70 | 1.36 | 5.40 | 5.40 |
| 256 KiB | 0.68 | 4–18 | 5.38 | 8–23 |
| 64 MiB | 0.86 | 18.2 | 5.48 | 24.2 |

With APB the loop runs at the same speed from memory as from L1; without
it, it runs at the memory latency, since lcc's code without APB does not
prefetch. (`dot` is bound by its chain of FP additions while the data is
in L1.)


One area delivers at most **16 bytes a cycle** (4C and 8C2; lcc's
loops in timing.md, "Array prefetch"): lcc's v5 code, which reads 32
bytes an iteration from one area with two `movaqp`, runs no faster per
element than its v3 code with two `movad`.

**Area size is the prefetch depth.** `apb-stream.c` (generated by
`gen_apb_stream.py`) streams one array through one area in a
one-instruction `loop_mode` loop, one `movad` per iteration consumed six
iterations later, for every `asz` and `dcd`, in cycles per element
(best of five; memory: 4 Mi elements of a 512 MiB array, the 4C on one
NUMA node; reproducible within 1%):

| `asz` (area) | L1, 4C | L1, 8C2 | memory, 4C | memory, 8C2 | memory, a line per `mova` (step 8), 4C | the same, 8C2 |
|---|---|---|---|---|---|---|
| 0 (64 B) | 2.5 | 1.5 | 12.1 | 10.4 | 12.4 | 12.2 |
| 1 (128 B) | 1.25 | 1.0 | 6.2 | 5.5 | 6.4 | 5.9 |
| 2 (256 B) | 1.0 | 1.0 | 3.1 | 2.9 | 3.7 | 3.4 |
| 3 (512 B) | 1.0 | 1.0 | 1.6 | 1.5 | 3.2 | 3.2 |
| 4 (1 KiB) | 1.0 | 1.0 | 1.1 | 1.15 | 3.2 | 3.2 |
| 5 (2 KiB) | 1.0 | 1.0 | 1.05 | 1.14 | 3.3 | 3.2 |

- From memory, each doubling of the area roughly halves the time per
  element until about 1 KiB (`asz` 4), where a stream from memory runs
  nearly as fast as from L1. A one-instruction loop needs `asz` ≥ 2
  (4C) or ≥ 1 (8C2) to run an element per cycle even from L1.
- An area fetches at most one new 64-byte line every 2 cycles from L1
  and about one every 3.2 cycles from memory (step 8), on both machines.
- `dcd` changes nothing on the 8C2. On the 4C, `dcd` 2 and 3 slow the
  line rate from memory to one every 5.5 cycles (step 8), and `dcd` 3
  also slows consecutive elements (9.4 cycles at `asz` 1–2, 6.9 at 3,
  3.05 at 4, 1.64 at 5); `dcd` 2 with consecutive elements costs
  nothing. So `dcd` 0, as lcc writes, is never faster for the stream
  itself; the other values pay off for the data around it (below).
- lcc gives each half of the buffer 32 units (2 KiB): with three
  arrays, areas of 512 B, 512 B and 1 KiB.

Several arrays at once (`multi*` cases: K areas 64 MiB apart, one
`movad` from each per iteration, areas 0 and 1 in the left half, 2 and
3 in the right; cycles per iteration):

| Arrays × area | consecutive elements, memory: 4C | 8C2 | a line per element, L1: 4C, 8C2 | a line per element, memory: 4C | 8C2 |
|---|---|---|---|---|---|
| 1 × 1 KiB | 1.10 | 1.19 | 2.0 | 3.2 | 3.2 |
| 2 × 1 KiB | 1.19 | 1.21 | 2.0 | 7.4 | 6.7 |
| 4 × 1 KiB | 1.85 | 1.75 | 2.0 | 15.1 | 14.8 |
| 2 × 512 B | 1.82 | 1.73 | 2.0 | 7.3 | 6.7 |
| 4 × 512 B | 2.39 | 2.06 | 2.0 | 14.7 | 13.6 |

The 2-cycle line limit from L1 is per area (four areas fetch four lines
in 2 cycles), but from memory all areas share one rate of about a line
every 3.2–3.75 cycles: about 14 GB/s on the 4C (0.8 GHz, two of three
memory channels populated) and 27 GB/s on the 8C2, for one core. Larger
areas still help when several streams compete (4 × 1 KiB against
4 × 512 B).

**Several cores** (`apb-stream one CASE T`: copies pinned to cores,
starting together, the timed loop only, mean of 40 runs from memory; a
line per element, cycles per line per core):

| Cores | 8C2 | 8C2 total | 4C, one node | 4C total |
|---|---|---|---|---|
| 1 | 3.2 | 30 GB/s | 3.4 | 15 GB/s |
| 2 | 3.9 | 49 GB/s | 6.1 | 17 GB/s |
| 4 | 6.3 | 61 GB/s | 12.2 | 17 GB/s |
| 8 | 13.7 | 56 GB/s | | |

Consecutive elements reach the same totals (8 cores of the 8C2: 1.73
cycles per element each, 55 GB/s; 4 cores of a 4C node: 1.74, 15 GB/s).
One 4C core nearly saturates its node's memory (two DDR3 channels
populated); the 8C2 (four DDR4 channels) needs about four cores.

**`dcd` and other cached data** (`apb-stream hot CASE KB`: reread a
working set, one load a line, before and after streaming 32 MiB through
one 1 KiB area; ns per line, best of five; the 4C on one node):

| Working set | 4C `dcd` 0 | 4C `dcd` 2, 3 | 8C2 `dcd` 0 | 8C2 `dcd` 2 | 8C2 `dcd` 3 |
|---|---|---|---|---|---|
| 48 KiB | 8.4 → 31 | 8.4 → 10.3–10.7 | 5.2 → 117 | 5.3 → 120 | 5.3 → 6.1 |
| 256 KiB | 18.8 → 121 | 18.8 → 18.8 | 12.3 → 108 | 11.9 → 113 | 9.7 → 16.4 |
| 1 MiB | 18.7 → 120 | 18.7 → 19–33 | 23.5 → 104 | 23.5 → 116 | 23.9 → 24.1 |
| 4 MiB | memory both ways | memory both ways | 24.2 → 105 | 24.0 → 109 | 24.0 → 24.0 |

A stream with `dcd` 0 evicts everything, on the 8C2 also a working set
in L3. `dcd` 2 keeps it on the 4C and does nothing on the 8C2; `dcd` 3
keeps L1, L2 and L3 on the 8C2. Combined with the speeds above: for a
large array read once, `dcd` 2 on the 4C (consecutive elements: no
cost) and `dcd` 3 on the 8C2 (no cost at all) protect the rest of the
cache; lcc never does this. Data read with them is not cached for a
later loop either.
## AAU stores [lcc, source, hw]

`staa{b,h,w,d,q}` (channels 2 and 5) store to `AAD[d].base +
AASTI[ind] + literal`; an `incr,CH %aaincrN` on the next line (encoded
in the CDS AM2/AM5 bit) adds `AAINCR[N] × size` to `AASTI[ind]` after
the store. lcc uses them for stores in APB loops (`d[i] = a[i] + 1`:
`staad %b[15], %aad1[ %aasti1 ]`, `incr,5 %aaincr2`). They do not need
`bap`. On the 4C (`tools/isa-probes/loops.c`, `aastores*`): with
`aaurwd` of the base to `%aad0` and 0 to `%aasti1`, `staad,5 v, %aad0[
%aasti1 ]` with `incr,5 %aaincr0` stores consecutive doublewords, and
in a `loop_mode` instruction it obeys the loop-mode store rules like
any store, **including its `incr`**: a suppressed `staa` doesn't advance
the index, so the first iteration after the prologue stores at element 0
([loops.md](loops.md)).

Other formats on the 4C (`aastores{b,h,w,q}*`, `aastores_lit`):
`staab`, `staah` and `staaw` store the low 8, 16 and 32 bits of their
register and step 1, 2 and 4 bytes, under the same loop-mode rules (with
`pcnt` 3 and `strmd` 1, iterations 4–7 land in elements 0–3); a literal
(`%aad0[ %aasti1 + 0x8 ]`) is a byte offset added to the address (one
doubleword further), the index stepping as without it; `staaq %qrN` stores `%drN` at
the lower and `%drN+1` at the higher address and steps 16 bytes (the
area 16-byte aligned). In loop mode a `staaq` counts as two stores for
`strmd`, and splitting it raises SIGILL ([loops.md](loops.md)). With
its data ready it costs what a `staad` does; with the data written by
integer ops two cycles before, the loop took 4 more cycles per
iteration (one stall step; not analysed further) [hw].

**AAU stores need no alignment**, unlike the movas of array prefetch on
v3: `staad` from a base 1, 2 or 4 bytes off a doubleword and `staaw` 2
bytes off a word, four elements with `incr %aaincr0`, write exactly the
right bytes at the misaligned addresses and nothing else, with no signal,
on the 4C, 8C2 and 2C3 (`tools/isa-probes/pocchk2.c` `staad_mis`,
`staaw_mis`; the proof-of-concept back end's I43). So a compiler may use
AAU stores for arrays of unknown alignment on every version; only the
loads through APB need aligned elements on v3 and v4 (above).

A warning from the 8C2: an area whose increment carried a `mova` 32 GiB
past its array (into unmapped memory) did not give a diagnostic value
as nearer unmapped addresses do; the process spun in the kernel
(nearly all system time, no page faults) until killed. The probe now
maps the page its 64-bit step reaches; don't point APB areas that far
on shared machines.

## 128-bit movas (v5+) [hw: Elbrus-8C2]

`movaqp,N area=…, ind=…, am=…, be=…, %qprM` (`apb.c` built with
`-DAPB_V5`, cases `q5*`) with an area of `fmt` 5 returns 16 bytes per
element into all of `%qprM` and steps 16 bytes. A base misaligned by 8
or by 4 bytes still returns the right (unaligned) 16 bytes, as v5's
doubleword movas do with a misaligned base (the 4C gives a diagnostic
value there). `be = 1` reverses all 16 bytes (the low half of the
result is the swapped high doubleword). An area with `fmt` 7 makes the
`movaqp` SIGILL on the 8C2.

## How lcc uses APB [lcc, guide]

- At `-O2` and above (not `-O1`), also when software pipelining is
  off (`-fswp-maxopers=0`, guide 6.3.6), for counted loops with no calls whose loads have an address linear in
  the iteration (`a[i]`, `a[k*i + c]`, `p++`, structure fields); reads
  of up to 32 bytes per array per iteration (more are split into
  several areas). Up to 32 arrays and 8 increments [guide 6.6]. lcc's v3
  code stops at 32 areas (NPB SP's xi-flux loop: 32 areas and 5 plain
  loads); its v5 and v6 code reads more arrays through one descriptor
  with the start addresses in `%aaind` (that loop: all 37 loads, 22
  descriptors and 15 `%aaind` indices) [lcc; the PoC's P57].
- On v3 it needs alignment of 2-, 4- and 8-byte elements: at `-O3` and
  `-O4` it uses APB only where it can prove it (global arrays, a pointer
  passed through `__builtin_assume_aligned`) or with `-faligned` or
  `-ffast`, which let it assume it; a loop over a plain pointer gets no
  APB (lcc 1.29.16 for v3 and v3.4c, 1.31.05; no run-time alignment
  check was seen, although lcc's changelog mentions versioning).
  On v5 and v6 it uses APB for the same loops without any of these.
  Byte arrays never got APB in our probes.
- It always writes `dcd = 0` (`-O3`, `-O4`, `-ffast`, `#pragma vector
  nontemporal`; v3, v5, v6).
- Prologue: `ldisp`, the AAU writes, `rwd %lsr`, the first iterations'
  elements loaded with ordinary `ld` into the rotating registers, then
  `bap` and a `ct %ctpr1` into the loop.
- The movas write rotating registers (`%b[]`), which the loop's
  consumers read several iterations later.
- `-fno-loop-apb` disables it; glibc's E2K string functions use
  `#pragma noprefetch` or `#pragma loop count` to stop lcc from using it
  on short loops.

## Generations [lcc-doc]

| ISA | Capability |
|---|---|
| v2–v4 | Only loads aligned to their size; lcc proves alignment statically or by versioning the loop at run time |
| v5 | Unaligned loads; 64-bit `%aaind`; loads of different sizes from one array can share one prefetch area; `movaqp` |
| v6 | Strides that are not a multiple of the load size; the head of a prefetch area can advance several times per iteration; the kernel saves `%aaldi` directly (lcc 1.31; all three checked on the 2C3: "v6", below) |

Loops on v5+ also have a 64-bit hardware loop counter (lcc 1.25), so lcc
no longer splits loops whose trip count may not fit in 32 bits.

## Hardware bug in code placement [source]

`CPU_HWBUG_CODE_PLACEMENT` (MCST bugs 146897, 140436, 77417; E2S, E8C,
E1CP, E8C2, E12C, E16C, E2C3 rev ≤ 1): jumps to the end of a 4 KiB page
"and placement of asynchronous program code" can misbehave; branch
targets and return addresses must avoid page offsets 0xdc0–0xdf8 and
0xee0–0xff8 (kernel `cpu_features.h`). MCST gas works around it by
default for v2–v6 (`ENABLE_FIX_LCC_BUG_142105`): it moves labels and
call return addresses out of those ranges and aligns code sections to
1 KiB. The rule for the APB program itself is not published. Other
errata and our own unconfirmed observations (one on APB programs on the
2C3) are in [hwbugs.md](hwbugs.md).

## Emulators

Neither qemu buffers anything: both read memory when the `mova`
executes, and neither models buffer areas, alignment on v3 or timing.
Of `apb.c`'s first 76 cases MCST's qemu matches the 4C in 63, the
community qemu in 64; all address arithmetic, `am`, `ind`, `be`, narrow movas,
the halves and the areas agree. Differences:

| Case | 4C | MCST's qemu | Community qemu |
|---|---|---|---|
| Signal handler during a `loop_mode` APB loop | correct | **wrong data**: `sigreturn` restarts every area from its start (`linux-user/e2k/signal.c`); lcc's loops in `apb-lcc.c` give 600 wrong results of 900 | correct |
| Trap between movas outside loop mode | position from the loop counters | continues | continues |
| `ind + size > mrng`, `mova` wider than `fmt` | diagnostic | diagnostic (other bits) | data; SIGILL |
| Misaligned base, overlapping areas | diagnostic (the 8C2, v5: a misaligned base gives the unaligned data; of two overlapping areas the first gives data, the second diagnostic) | data | misaligned: invalid value without a tag; overlap: data |
| `mova` after `eap`, after a write to `%ctpr2` | SIGILL | data | data |
| `mova` after a call | SIGILL | aborts (no signals for hardware exceptions) | SIGILL |
| `eap` then `bap` | continues | continues | restarts from the start |
| `aaurw 0, %aabf0` | movas diagnostic after the next trap | no effect | later movas invalid |
| A store to an element already prefetched | old value | stored value | stored value |
| `dpl = 1` | right half streams the left half's array | the same | right half's own fields |
| `aaurrd` | reads 0 | unimplemented, aborts | SIGILL |
| `movaq` | high half at `ind + 8` | crashes | aborts |

So APB code has to be tested on hardware, and code built by lcc with
APB (`-O2` and above) can give wrong results under MCST's qemu when the
program receives signals.

## v6 [hw: Elbrus-2C3]

`apb.c` (with the v5 cases), `apb-stream.c` and `apb-lcc.c` built by the
2C3-tuned lcc, run on the 2C3 next to the 8C2. Address arithmetic,
`am`, `ind`, `be`, narrow movas, halves, areas, `movaqp`, the stores
the buffer doesn't see, `dpl`, `dcd`, `%aabf0`, the SIGILL after a call,
a return, `eap` or a `%ctpr2` write: all as on the 8C2. What differs:

| | 8C2 (v5) | 2C3 (v6) |
|---|---|---|
| Trap (page fault, signal handler) between movas outside a loop | positions recomputed from the loop counters: the next element repeats | **positions kept**: the next `mova` continues where it was (the kernel saves `%aaldi`, above). Inside a `loop_mode` loop both are correct; an ordinary branch loop is correct only on v6 (Traps, above) |
| `mova` wider than `fmt` (`movad` on `fmt = 3`) | diagnostic | **data** (the 8 bytes at the position) |
| A byte area read by `movad` with a 12-byte step, a half area by `movaw` with a 6-byte step, `movad` at `ind` 4 of a byte area (`w12`, `w6`, `w_ind4`) | diagnostic | **the bytes at each position**, unaligned: a step need not be a multiple of the read (lcc 1.31's APB for such strides, "from Elbrus V6") |
| Diagnostic value | `eaed0f70eaed0f70`, tag 1 | `4000000040000000`, tag 1 |
| `aaurrd %aaldi0` after two `movad` | 0x40 | 0x10 (the position in bytes) |
| Bytes one area delivers a cycle | 16 | **32**: lcc's two-`movaqp` loop runs an iteration a cycle (`apb-lcc.c` sum of `long`s: 0.14 ns, 0.28 cycles, per element) |
| A line per `mova` (step 8), from L1 | a line every 2 cycles per area | a line a cycle; with 2 areas in one half 2 cycles, 4 areas (two per half) 2 cycles |
| The same from memory, one area | 3.2 cycles | 2.7 |
| Consecutive elements from memory, `asz` 0 … 5 | 10.4, 5.5, 2.9, 1.5, 1.15, 1.14 | 11.4, 5.8, 2.9, 1.47, 1.10, 1.10 |
| `mova` → consumer | (see Timing) | 5 cycles; a consumer 1–4 cycles after it stalls 4 |
| First `mova` without a stall after `bap` | 20 cycles of `nop` (`gap20`) | 18 (`gap18`) |

lcc's loops pass on the 2C3: 0 wrong of 900 results under about 10,000
timer signals, and the guard page case; APB makes its sum 19× and its
dot product 7× faster on a 64 MiB array there.
