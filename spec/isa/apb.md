# Array prefetch (APB)

The array access unit (AAU) runs a small program of `fapb` entries
alongside the main instruction stream. Each entry streams one array
into a region ("area") of the array prefetch buffer (APB); the loop body
then reads the elements with `movaX` operations in four dedicated
channels instead of loads. A `mova` takes no ALU channel and has a fixed
latency, whatever the memory latency. The AAU also has stores with an
address register that increments itself (`staa` + `incr`).

This page is what a compiler needs to use APB correctly: the program
format, what a `mova` reads, what stops the unit, how traps interact
with it, and what it costs. Encodings of the syllables are in
[bundle.md](bundle.md) (AAS, SS `bap`/`eap`, CS0 `ldisp`); loop mode is
in [control-transfer.md](control-transfer.md).

## Model [guide, source]

1. Write the AAU registers the program uses: array descriptors `%aadN`,
   start indices `%aaindN`, increments `%aaincrN` (`aaurw`/`aaurwd`/
   `aaurwq`, channels 2 and 5).
2. `ldisp %ctpr2, label` loads the program at `label`. Only `%ctpr2`
   can hold it.
3. `bap` ("begin array prefetch") starts it. From now on the AAU fetches
   each area's elements ahead of use, independently of the main stream.
4. In the loop, `movaX` operations read elements from the areas; a `mova`
   with `am = 1` advances its area by one step after the instruction.
5. The program ends when `%ctpr2` is overwritten (lcc writes
   `disp %ctpr2, disp=0x0` after the loop) or at the next call or return.

`eap` ("end array prefetch") pauses the program: a `bap` after it
resumes where it stopped [hw].

## The program [source: gas; hw]

An APB instruction is 16 bytes with no header: a left half (APS0 +
APLS0) and a right half (APS1 + APLS1), 8 bytes each. In assembly one
`{ }` group holds up to two `fapb` entries: the one written with `ct=`
is the left half, the one with `dpl=` the right half. gas fills an
absent half with zeros. The program follows the function's code (lcc
places it after the loop's prologue, jumped over, after `.align 8`).

```
	.align	8
.Lprog:
	{
	  fapb	ct=0, dcd=0, fmt=4, mrng=16, d=4, incr=1, ind=0, asz=3, abs=0, disp=0
	  fapb	dpl=0, dcd=0, fmt=4, mrng=16, d=3, incr=1, ind=0, asz=4, abs=0, disp=0
	}
	{
	  fapb	ct=1, dcd=0, fmt=4, mrng=16, d=2, incr=1, ind=0, asz=4, abs=16, disp=0
	}
```

APS fields (APLS is the 32-bit `disp`):

| Bits | Field | Meaning |
|---|---|---|
| 31 | `ct` (left) / `dpl` (right) | `ct = 1`: last instruction of the program; it must be set in the last instruction's left half. `dpl = 1`: the right half duplicates the left; lcc always writes 0 |
| 30 | `si` | Secondary index, v1 only; gas rejects it on v2+ |
| 28–29 | `dcd` | Cache control: 0 all caches; 2 bypass DCACHE2; 3 bypass DCACHE2 and ECACHE [guide]. lcc writes 0 |
| 25–27 | `fmt` | Element format: 1 byte, 2 half, 3 word, 4 double, 5 quad, 7 quad packed (v5+). Used to scale the increment and to check alignment |
| 20–24 | `mrng` | Bytes a `mova` may read per step, from 1 to 31; 0 means 32 |
| 15–19 | `d` | Descriptor `%aadN` (0–31) |
| 12–14 | `incr` | Increment register `%aaincrN` (0–7); `%aaincr0` is always 1 |
| 8–11 | `ind` | Start-index register `%aaindN` (0–15); `%aaind0` is always 0 |
| 5–7 | `asz` | Area size: 64 × 2^asz bytes; gas accepts 0–5 |
| 0–4 | `abs` | Area base in the buffer, in 64-byte units; must be a multiple of the area size (gas checks) |

Instruction *i*'s left half describes **area *i*** and its right half
**area 32 + *i***, so a program has at most 32 instructions [source:
kernel `traps.c`, qemu]. The unit for `asz` and `abs` is the guide's;
no other source gives one, and lcc's programs fill each half with
exactly 32 units (`asz` 3 + 3 + 4 above = 8 + 8 + 16).

## Registers [source; lcc]

| Register | Count | Width | Meaning |
|---|---|---|---|
| `%aadN` | 32 | 128 | Array descriptor: base address in bits 0–47 of the low half (plus tag, rw bits); size in the high half up to v6 |
| `%aaindN` | 16 | 32 (v3, v4), 64 (v5+) | Start index in bytes; `%aaind0` = 0 |
| `%aaincrN` | 8 | 32, sign-extended (v3, v4), 64 (v5+) | Step in elements; `%aaincr0` = 1 |
| `%aastiN` | 16 | as `%aaind` | Store index for `staa` |
| `%aaldiN`, `%aaldaN`, `%aaldv`, `%aaldm`, `%aafstr`, `%aasr` | | | Current positions and state; the kernel saves them on traps |
| `%aabfN` | | | Write-only; "value for modification of AAU load flags" (binutils), meaning not documented |

`aaurwd` to a `%aad` sets the base and the rw bits and clears the high
half (qemu). User code can execute `aaurrd` on the 4C, but every
register read that way returned 0 [hw], so the state is not observable.

How lcc sets them up:

| | v3, v4 | v5, v6 |
|---|---|---|
| Array address | in the descriptor: `aaurwq %rN, %aadK` with the base in `%rN` and 0 in `%rN+1` | in a start index: `aaurwd %rN, %aaindK` (64-bit); the descriptor gets base 0 (`aaurw`) |
| Step | `aaurw n, %aaincr1` (elements) | `aaurwd n, %aaincr1` |

## What a mova reads [hw]

```
movaX,CH area=A, ind=I, am=M, be=B, %dst      CH = 0..3
```

Channels 0 and 1 read areas 0–31 (left halves), channels 2 and 3 areas
32–63 (right halves): `area` names the instruction, the channel picks
the half. The area's first element is at

```
start = AAD[d].base + AAIND[ind] + disp
```

and each step adds `size(fmt) × AAINCR[incr]` bytes (negative increments
work). A `mova` reads `size(X)` bytes at `current + I`.

| Behaviour | Observed |
|---|---|
| `am = 1` | Advances the area by one step after the instruction; several `am = 1` movas on one area in one instruction advance it once. Without `am` the area stays put |
| `ind` | Byte offset inside the step, 0–31: `mrng = 32` with `movad` at `ind` 0, 8, 16, 24 reads four consecutive doubles |
| `movab`, `movah`, `movaw` | Zero-extended |
| `be = 1` | Byte-swapped; for `movaq` the whole 16 bytes |
| `movaq,0 ind=I` | Low half from `I`, high half from `I + 8` (gas writes it as two AAS entries, `ind` I and I + 8, in channels 0 and 1); `movaq,2` likewise in channels 2 and 3 |
| `movaq` / `movaqp` | Quad registers; `movaqp` is v5+ (lcc uses it on v5, v6 with `fmt = 5`, `mrng = 0`) |

### Diagnostic results [hw]

While the program runs, a `mova` never traps (for one that runs after
the program stopped, see the next section). When it cannot deliver data
it writes a diagnostic value (tag 1 in both halves, bits
`eaed0f70eaed0f70`), which then behaves like any other diagnostic
operand. Cases seen:

| Case | Result |
|---|---|
| `ind + size > mrng` | diagnostic |
| `mova` wider than `fmt` (`movad` on `fmt = 3`) | diagnostic |
| Base not aligned to `fmt` (v3) | diagnostic. lcc versions loops or needs `-faligned` [lcc]; v5 allows unaligned 2, 4, 8 bytes and v6 16 bytes [guide, lcc-doc] |
| Two areas whose `abs`/`asz` overlap | diagnostic |
| Element in an unmapped page | diagnostic; no signal. The prefetch running past the end of an array into an unmapped page is harmless (lcc's loops over arrays that end at a `PROT_NONE` page are correct) |

The kernel handles an AAU page fault speculatively: it maps the page if
it can and otherwise marks the access invalid, without a signal
[source: kernel `do_aau_fault`, `mm/fault.c`].

## Starting, pausing and stopping [hw]

| Between movas of one stream | Next `mova` |
|---|---|
| `call` (to a function that just returns) | **SIGILL** |
| `disp %ctpr2, ...` (any write to `%ctpr2`) | **SIGILL** |
| `eap` | **SIGILL** |
| `eap` ... `bap` | continues where it stopped |
| `disp %ctpr1, ...` | continues |
| `aaurw 0, %aabf0` | continues |
| a page fault or a signal handler | continues, but see "Traps" below |

A call or return resets the AAU [source: qemu `translate-ct.c`; kernel
comments in `ttable.c`], so APB can be used only in loops without calls
[guide 6.6], and a `mova` after a call (even in a later, separate loop)
must follow its own `ldisp` and `bap`. System calls also reset it (they
are reached through calls anyway). The kernel itself is built with
lcc's `-fno-loop-apb` and keeps `%ctpr2` free in trap code.

After the loop lcc writes `{ disp %ctpr2, disp=0x0; aaurw,2 0, %aabf0 }`
and never uses `eap`. What the `%aabf0` write does is not documented and
had no visible effect.

## Traps, signals and the loop counter [hw, source]

The kernel stops the AAU on every trap and interrupt, saves its state
and restarts it on return [source: kernel `ttable.c`]. On return it does
not restore each area's position: it **recomputes** it as

```
start + step × iterations,  iterations = %ilcr.lcnt − %lsr.lcnt
                            (+ the epilogue count when lcnt reached 0)
```

(`kernel/cpu/iset_v3.c`; v6 saves the positions instead). So the number
of `am` advances of every area must equal the number of loop-mode
iterations done, **at every instruction where an interrupt can arrive**.
Interrupts arrive at any instruction (timer, other CPUs), so this is a
correctness rule, not a corner case. `apb-loop.c` shows it on the 4C:

| Loop (sum of 1M elements, 200 runs) | Result |
|---|---|
| `loop_mode` loop counted by `%lsr`, one `am = 1` per area per iteration, `%lsr` written before `bap` | correct in every run, also with a SIGALRM every 100 µs (about 21,000 signals) |
| Ordinary branch loop with the same movas | wrong in every run, even without extra signals |
| `loop_mode` loop, but `%lsr` written after `bap` and a page fault between them, after a 777-iteration loop | the stream is shifted by exactly 777 elements; correct without the fault |

lcc's loops (`apb-lcc.c`: one array, two arrays with a stride and an
offset, a dot product) gave 0 wrong results in 900 with about 34,000
signals, and with three processes sharing one CPU.

Rules that follow:

- Use APB only in a `loop_mode` loop counted by `%lsr`
  ([loops.md](loops.md); `ct %ctpr1 ? %NOT_LOOP_END`, `alc alcf=1,
  alct=1`), with every area advanced (`am = 1`) exactly once per
  iteration.
- Write `%lsr` (which also sets `%ilcr`) before `bap`, and issue no
  `mova` outside the loop.
- In the prologue between `bap` and the loop, no area may advance.

## Timing [hw]

On the 4C (elbrus-v3), data in L1 or L2:

| | Cycles |
|---|---|
| `bap` → first `mova` without a stall | 22 (a `mova` issued earlier stalls in steps of 4 cycles; lcc leaves 17–24) |
| `bap` → first data from memory | about 160–250 more |
| `mova` → consumer | 5, in any channel or cluster; a consumer issued earlier stalls a fixed 4 cycles |
| `mova` issue | up to four per instruction, every cycle |

lcc's loops with and without APB (`apb-lcc.c`, ns per element at about
0.8 GHz; `-fno-loop-apb` turns APB off):

| Array | `sumd` APB | `sumd` no APB | `dot` APB | `dot` no APB |
|---|---|---|---|---|
| 16 KiB | 0.70 | 1.36 | 5.40 | 5.40 |
| 256 KiB | 0.68 | 4–18 | 5.38 | 8–23 |
| 64 MiB | 0.86 | 18.2 | 5.48 | 24.2 |

With APB the loop runs at the same speed from memory as from L1; without
it, it runs at the memory latency, since lcc's code without APB does not
prefetch. (`dot` is bound by its chain of FP additions while the data is
in L1.)

## AAU stores [lcc, source, hw]

`staa{b,h,w,d,q}` (channels 2 and 5) store to `AAD[d].base +
AASTI[ind] + literal`; an `incr,CH %aaincrN` on the next line (encoded
in the CDS AM2/AM5 bit) adds `AAINCR[N] × size` to `AASTI[ind]` after
the store. lcc uses them for stores in APB loops (`d[i] = a[i] + 1`:
`staad %b[15], %aad1[ %aasti1 ]`, `incr,5 %aaincr2`). They do not need
`bap`. On the 4C (`tools/isa-probes/loops.c`, `aastores*`): with
`aaurwd` of the base to `%aad0` and 0 to `%aasti1`, `staad,5 v, %aad0[
%aasti1 ]` with `incr,5 %aaincr0` stores consecutive doublewords, and
in a `loop_mode` instruction it obeys the loop-mode store rules like
any store, **including its `incr`**: a suppressed `staa` doesn't advance
the index, so the first iteration after the prologue stores at element 0
([loops.md](loops.md)).

Other formats on the 4C (`aastores{w,q}*`): `staaw` stores the low 32
bits of its register and steps 4 bytes; `staaq %qrN` stores `%drN` at
the lower and `%drN+1` at the higher address and steps 16 bytes (the
area 16-byte aligned). In loop mode a `staaq` counts as two stores for
`strmd`, and splitting it raises SIGILL ([loops.md](loops.md)). With
its data ready it costs what a `staad` does; with the data written by
integer ops two cycles before, the loop took 4 more cycles per
iteration (one stall step; not analysed further) [hw].

## How lcc uses APB [lcc, guide]

- At `-O2` and above (not `-O1`), also when software pipelining is
  off (`-fswp-maxopers=0`, guide 6.3.6), for counted loops with no calls whose loads have an address linear in
  the iteration (`a[i]`, `a[k*i + c]`, `p++`, structure fields); reads
  of up to 32 bytes per array per iteration (more are split into
  several areas). Up to 32 arrays and 8 increments [guide 6.6].
- On v3 it needs alignment of 2-, 4- and 8-byte elements: with
  `-faligned` it assumes it, otherwise it checks the address at run time
  and keeps a copy of the loop without APB. Byte arrays never got APB in
  our probes.
- Prologue: `ldisp`, the AAU writes, `rwd %lsr`, the first iterations'
  elements loaded with ordinary `ld` into the rotating registers, then
  `bap` and a `ct %ctpr1` into the loop.
- The movas write rotating registers (`%b[]`), which the loop's
  consumers read several iterations later.
- `-fno-loop-apb` disables it; glibc's E2K string functions use
  `#pragma noprefetch` or `#pragma loop count` to stop lcc from using it
  on short loops.

## Generations [lcc-doc]

| ISA | Capability |
|---|---|
| v2–v4 | Only loads aligned to their size; lcc proves alignment statically or by versioning the loop at run time |
| v5 | Unaligned loads; 64-bit `%aaind`; loads of different sizes from one array can share one prefetch area; `movaqp` |
| v6 | Strides that are not a multiple of the load size; the head of a prefetch area can advance several times per iteration; the kernel saves `%aaldi` directly |

Loops on v5+ also have a 64-bit hardware loop counter (lcc 1.25), so lcc
no longer splits loops whose trip count may not fit in 32 bits.

## Hardware bug in code placement [source]

`CPU_HWBUG_CODE_PLACEMENT` (MCST bugs 146897, 140436, 77417; E2S, E8C,
E1CP, E8C2, E12C, E16C, E2C3 rev ≤ 1): jumps to the end of a 4 KiB page
"and placement of asynchronous program code" can misbehave; branch
targets and return addresses must avoid page offsets 0xdc0–0xdf8 and
0xee0–0xff8 (kernel `cpu_features.h`). MCST gas works around it by
default for v2–v6 (`ENABLE_FIX_LCC_BUG_142105`): it moves labels and
call return addresses out of those ranges and aligns code sections to
1 KiB. The rule for the APB program itself is not published.

## Emulators

Neither qemu buffers anything: both read memory when the `mova`
executes, and neither models buffer areas, alignment on v3 or timing.
Of `apb.c`'s 76 cases MCST's qemu matches the 4C in 63, the community
qemu in 64; all address arithmetic, `am`, `ind`, `be`, narrow movas,
the halves and the areas agree. Differences:

| Case | 4C | MCST's qemu | Community qemu |
|---|---|---|---|
| Signal handler during a `loop_mode` APB loop | correct | **wrong data**: `sigreturn` restarts every area from its start (`linux-user/e2k/signal.c`); lcc's loops in `apb-lcc.c` give 600 wrong results of 900 | correct |
| Trap between movas outside loop mode | position from the loop counters | continues | continues |
| `ind + size > mrng`, `mova` wider than `fmt` | diagnostic | diagnostic (other bits) | data; SIGILL |
| Misaligned base, overlapping areas | diagnostic | data | misaligned: invalid value without a tag; overlap: data |
| `mova` after `eap`, after a write to `%ctpr2` | SIGILL | data | data |
| `mova` after a call | SIGILL | aborts (no signals for hardware exceptions) | SIGILL |
| `eap` then `bap` | continues | continues | restarts from the start |
| `aaurw 0, %aabf0` | no effect | no effect | later movas invalid |
| `aaurrd` | reads 0 | unimplemented, aborts | SIGILL |
| `movaq` | high half at `ind + 8` | crashes | aborts |

So APB code has to be tested on hardware, and code built by lcc with
APB (`-O2` and above) can give wrong results under MCST's qemu when the
program receives signals.
